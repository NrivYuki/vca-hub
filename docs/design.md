# vca-hub 設計書

眼鏡店・ラボの機器と PC の間で VCA 通信(DCS v3.14)のデータを受け取り、ローカルフォルダに保持し、任意の送信先へ中継する常駐プログラム。

この文書は vca-hub の設計をまとめたものである。主な決まりは 12 章、拡張は 13 章にまとめる。

## 1. 目的と範囲

- 必須条件: 送られてきたデータをローカルフォルダに保持し、任意の送信先にそのまま送信(中継)できること
- 受信元: トレーサー、別の PC(機器としてアップロードしてくる場合、または共有フォルダにファイルを置く場合)
- 送信先: 加工機、別の PC やソフト、共有フォルダ
- 接続: LAN(TCP/IP)。リモート接続、ローカル接続、オートコネクトの 3 方式
- 機器の機種は限定しない(規格どおりに動く機器を対象とする)
- 実行環境: Node.js(Windows を主対象とする)
- 配る形: インストールなしで動かす。node.exe を同梱したフォルダを zip にし、展開して起動用のファイル(`start.bat`)を開くだけで動くようにする(管理者の権限を要らなくするため)。データは同じフォルダの `data/` に置く。`start.bat` は同じフォルダの `node\node.exe` を先に使い、無ければ PC に入っている Node.js を使う(zip にする前の元のフォルダでも、同じ `start.bat` で起動できる)

### 中継の方針

- 受け取った原文は変えずに保存する(例外は 7 章の個人情報項目の除去を有効にした場合だけ)。送るときは送り先に合わせて組み立て直す。レコードの値は変えず、足りない項目を推測で埋めない。規格が求める形にそろえるもの(1 つしか置けないレコードの重なり、反転した玉型の寸法、機器ごとの値の当てはめ)と、送らないもの(サグ・注記・送り手の名乗り・機器ごとの値の行)は 6 章に書き、送る前の確認に出す
- 素材、ヤゲン位置、加工の種類などは加工機側で決める前提とし、vca-hub は扱わない。扱いたい利用者は拡張で足す(13 章)
- メーカー独自の項目や、規格から外れたメーカーの通信も、vca-hub 本体では扱わず、拡張で足す(13 章)
- 変えてよいのは、規格上必要な「入れ物」の部分だけとする
  - パケットの組み立て直し(通信用レコードの付け替え)
  - 玉型データの形式・点数・左右の向きを、送信先の機器が求める形に合わせること
  - 送信先が求めたレコードを持っていない場合に、値の代わりに `?`(不明)を入れること

### 範囲外

- レンズ設計、度数計算、厚み計算
- 処方を決めたり変えたりする機能(入れない)
- 足りない加工項目の入力・補完
- RS-232C(シリアル)接続。12 章の主な決まりを参照
- 管理画面の検索・設定画面、Windows のサービス化などの常駐化(設定は `config.json` で行う)

## 2. 前提となる規格上の制約

- 通信は必ず機器(デバイス)から始まる。ホストから機器へ一方的に送り付ける手順はない。vca-hub から接続しにいく場合(ローカル接続、オートコネクト)でも、接続後にセッションを始めるのは機器側である
- そのため「送信」は送信先ごとに次の形になる
  - 加工機: 保持したデータを送信待ちにしておき、加工機からの要求(`REQ=EDG` とジョブ番号)に応答する
  - 別の PC やソフト(相手がホスト): vca-hub が機器として相手へアップロードする(`REQ=UPL` または `REQ=TRC`)
  - 共有フォルダ: VCA ファイル(`REQ=FIL` 形式)として書き出す
- 受信も同様で、別の PC から受け取れるのは、相手が機器としてアップロードしてくる場合か、ファイルを置く場合に限られる
- 加工機はジョブ番号でデータを要求する。トレーサーには入力の手段が無く、意味のあるジョブ番号を送れないことがあるので、受け取ったデータには vca-hub で人が名前を付け、その名前を加工機・別の PC・共有フォルダへのジョブ番号にする(6 章の「名前」)

## 3. 全体構成

```
                         +--------------------- vca-hub(Node.js) ---------------------+
[トレーサー]    --LAN--> 接続部 --> セッション処理(ホスト役) --> 保存部 --> data/
[別の PC]       --LAN-->          |                                ^
[共有フォルダ]  ------> フォルダ監視 -------------------------------+
                         |                                                  |
[加工機]        <--LAN-- 接続部 <-- セッション処理(ホスト役) <-- 送信待ち一覧
[別の PC/ソフト] <-LAN-- 接続部 <-- セッション処理(機器役)   <-- 送信指示
[共有フォルダ]  <------ ファイル書き出し <------------------------- 送信指示
                         |
                         +- 管理画面(http://localhost:8765、この PC からのみ)
```

| 要素 | 役割 | 実装 |
|---|---|---|
| 接続部 | TCP の待ち受け・接続、オートコネクト(UDP)、許可する IP アドレスの確認 | vca-guide の `vca-tcp.js`。許可範囲の確認は vca-hub 側で行う |
| パケットの送受信 | FS から GS までの切り出し、ACK/NAK、再送、タイムアウト、CRC、同期ずれの検出 | vca-guide の `vca-session.js`(`createLink`) |
| セッション処理(ホスト役) | 初期化と形式の取り決め、アップロード受信、ダウンロード応答、時刻合わせ | `vca-session.js` の `createHost`。応答の中身は vca-hub が `onInit`・`onRequest`・`onData`・`onNotify` で返す |
| セッション処理(機器役) | 別の PC やソフトへのアップロード | `vca-session.js` の `createDevice` |
| 要求 ID の保存 | 初期化で割り当てた要求 ID と、機器が求めたレコード・玉型形式を再起動をまたいで保持する | vca-hub(`createHost` の `nextRequestId` と `onInit` につなぐ) |
| 保存部 | 受信データの保存、索引の更新、個人情報項目の除去(設定時) | vca-hub |
| 送信データ作成 | 保存データから送信用のレコードを組み立てる(1 章の中継の方針に従う) | vca-hub |
| フォルダ監視 | 指定フォルダに置かれた VCA ファイルの取り込み | vca-hub |
| 管理画面 | 一覧、玉型表示、送信前の確認、送信先の指定、送受信記録 | vca-hub |
| 読み書き | レコードの読み取り、玉型形式 1-4 の読み書き、点数の変換、ラベル定義表 | vca-guide の `vca-parser.js`・`vca-records.js` |

### vca-guide のライブラリの扱い

- `vca-parser.js`・`vca-records.js`・`vca-session.js`・`vca-tcp.js` の 4 つを vca-guide の `src` から `src/lib/` に写し、vca-guide と同じものに保つ(vca-lens-simulator・vca-ptn-converter も、このうち `vca-parser.js`・`vca-records.js` を写している)。同じであることはテスト(`tests/e2e.test.js`)で確かめる
- vca-hub で直したいところが見つかったら、vca-guide で直してから写し直す。vca-hub の中では書き換えない
- 写した元(vca-guide のコミット)と各ファイルの SHA-256(行末を LF にそろえたもの)を `src/lib/vca-guide.json` に残す。テストは、隣に vca-guide が無くても、写したときのままであることを確かめる
- 理由: パケットの送受信とセッションの手順は vca-guide 側で規格書から決めたテストと DCS Host Simulator との照合を経ており、同じものを vca-hub で別に持つと、直すたびに 2 か所の食い違いが生じるため
- 規格の読み方で vca-guide と同じ判断になるところ(STATUS の番号など)は、vca-guide の `docs/conformance.md` に従う
- vca-hub が使う、vca-guide のライブラリの働き
  - `vca-session.js` の `createHost` の `onComplete`: 要求のセッションの最後のパケットにデバイスが ACK を返したあとに呼ぶ。加工機が受け取ったことを確かめてから送信済みにするため
  - `vca-tcp.js` の `listenHost` の `opts` に渡す関数: 接続ごとに設定を作り、`null` なら接続を切る。相手のアドレスを記録に書くためと、許可範囲の外の相手を断るため
  - `vca-tcp.js` の `listenAutoconnect` の `opts.connectOpts`: オートコネクトでつなぐたびに設定を作る(同じ理由)

## 4. 接続(LAN)

規格の 3 つの接続方式すべてに対応する。

| 方式 | 動き | ポート |
|---|---|---|
| リモート接続 | vca-hub が待ち受け、機器から接続してくる | 33512(変更可) |
| ローカル接続 | 機器が待ち受け、vca-hub から接続しにいく(機器の IP を設定) | 機器側 50000(変更可) |
| オートコネクト | 機器が UDP で自分の IP とポートを知らせ、vca-hub がそこへ接続する | 33511 で受信 |

- 接続後、機器は 3 秒待ってからセッションを始める(規格の決まり)
- 別の PC やソフトへ送るときは、vca-hub が相手のホストへ接続する(相手の IP とポートを設定)
- 接続を受け付ける IP アドレス、オートコネクトで接続しにいく IP アドレス、ローカル接続の相手は、設定した許可範囲に限る(ローカル接続の相手が許可範囲の外なら起動しない)(VCA 通信自体には認証の仕組みがなく、不正な通知で意図しない相手に接続することを防ぐため)。許可範囲の既定はこの PC だけとし、機器のアドレスは利用者が書き足す(書き忘れたときに、LAN の全ての相手を通さないため)
- DCS には認証と暗号化の仕組みが無い(TLS は LDS との間だけ。5.9.7.3)。機器が対応していないので、vca-hub からも求めない。守りは許可範囲と、LAN の中で使うことによる
- 待ち受け(VCA)とオートコネクトで同時に開いておける接続の数を、全体と相手の IP ごとに限る(既定は全体 64、IP ごとに 8。`connections`)。オートコネクトは、つなぎに行っている途中のものも数え、上限に届いていれば知らせを断る(知らせの送り主は偽れるので、知らせを繰り返されても、つなぎに行く数が増え続けないように。つなげなかったものは 1 分で数から外す)。超えた接続はすぐに閉じ、記録に残す(同じ相手・同じ理由は 1 分に 1 度だけ書き、その間に断った数を添える)。接続には TCP の keepalive を使い、相手の電源が落ちたときなど閉じた知らせが届かない接続も OS が閉じて、数から外す(何も届かない時間が 60 秒を過ぎると確かめを始める)。何も送らない接続を時間では閉じない。規格はネットワークのセッションをシリアルと同じとし(7.8.2.3)、機器がつないだままにするのは正しい使い方のため
- オートコネクトの知らせは許可範囲の外からも届くので、断った知らせとつなげなかった記録も、同じ相手・同じ理由なら 1 分に 1 度だけ書く。つなげなかった相手のために作った接続の設定は、1 分で忘れる
- 許可範囲は IPv4・IPv6 のアドレスか範囲(`192.168.0.0/16`・`fd00::/8`)で書く。形の正しくない項目(範囲の長さの書き忘れ・33 以上の長さなど)があれば起動しない。書き損じを広い範囲として扱い、意図しない相手を通すことを防ぐため
- リモート接続は、すべての通信口で待ち受け、相手は許可範囲で限る(`vca-tcp.js` の `listenHost` は待ち受けるアドレスを選べないため)
- ローカル接続は、切れたら 10 秒後につなぎ直す

### 起動と停止

- 起動するときに `config.json` の知らない項目(書き損じ。`retentiondays` のような大文字・小文字の誤りも)、形と値の範囲を確かめ、誤りがあれば項目の名前を出して起動しない(`remote: true` のような書き方、ポートの書き損じ、`retentionDays` の 0・文字列、`extensions` の一覧の形、IP でないローカル接続の相手など)。書き損じを黙って別の意味に取ると、待ち受けない・個人情報を消さない、などが気付かれないまま続くため。JSON の誤りはファイルの名前を添えて出し、先頭の BOM は読み飛ばす
- 相対のパス(`dataDir`・`extensionsDir`・`exportDir`・`importDir`)は、起動したフォルダによらず vca-hub のフォルダを基準にする
- データのフォルダには、使っている vca-hub のプロセスの番号(`vca-hub.lock`)を置き、索引などを読む前に確かめる。別の vca-hub が同じフォルダを使っていれば起動しない(互いに索引を上書きして、受け取った記録が消えるため)。書いたプロセスがもう無ければ(異常終了など)引き継ぐ。その番号のプロセスがあっても、node でなければ引き継ぐ(電源断の後などは、止まった vca-hub の番号を別のプロセスが使っていることがあるため。Windows では tasklist で名前を見る)。名前を確かめられないときは、動いているとみなして起動しない
- ローカル接続でつなげないとき・送り先へ送れないときは、理由を現場で読める言葉で記録に残す(相手が待ち受けていない、応答が無い など。同じ理由は 1 分に 1 度)
- 古いロックの引き継ぎは、引き継ぎの印(`vca-hub.lock.takeover`)を排他で作れた 1 つの vca-hub だけが行う(ほぼ同時に 2 つ起動したとき、両方が引き継がないように)
- `config.json` の JSON の誤りは、行と、よくある誤り(最後の項目のあとのカンマ、パスの `\` を 1 つで書いている)を添えて出す。`\` を 1 つで書いて制御文字になったパス(`C:\new` の `\n` など)と、許可範囲の書き損じも、ほかの誤りと一緒に出す
- 記録はコンソールへ出さない(管理画面の「記録」と `data/log/` で見る)。cmd.exe の窓をクリックして選択の状態になると、コンソールへの出力が止まり、vca-hub 全体が止まるため。コンソールには、起動したことと、起動に失敗した理由だけを出す。書き込めない場所(Program Files など)から起動したときは、書き込めるフォルダへ展開し直すか `dataDir` を変えるよう案内する
- `start.bat` は、UNC のパス(`\\nas\...`)から開いても動くように、`pushd` で vca-hub のフォルダへ移り、`main.js` を vca-hub のフォルダから指す
- 止めるときは、管理画面の途中の要求も閉じる(待つと、ほかの口を閉じる前に止まるため)。Windows で窓を閉じたとき(SIGHUP)と Ctrl+Break(SIGBREAK)も、止める処理を通す

## 5. セッション処理

### ホスト役(受信と加工機への送信)

| 要求 | 対応 |
|---|---|
| `INI` | 自動フォーマット初期化に対応する。機器が示したレコード一覧に要求 ID を割り当てて返す。玉型形式(`TRCFMT`)・サグ(`ZFMT`)・文字コード(`TXTENC`)・穴あけの基準(`DRLFMT`。C・E・B のどれも受ける)は `VCA.negotiate` で取り決める(玉型は形式 1-4、角度のモードは E・U。サグは中継しないので `ZFMT=0`。文字コードは ASCII)。プリセット初期化(定義の無い初期化)も受け付ける。プリセット初期化をした機器の要求 ID には、機器の種類のプリセットの項目一式を返し、持っていない項目は `?` で返す(7.2.5.2・5.1.3・5.1.4。初期化しない機器と同じ) |
| `TRC`・`UPL`・`INS` | アップロードを受け取り、保存部へ渡す。要求に `TRCFMT` があれば、使うものを 1 つ応答に返し、`ZFMT` があれば `ZFMT=0` で答える(7.2.8)。扱える形式が無ければ `STATUS=17` を返し、データを受けない |
| `INF` | 作業完了の通知として記録する |
| `MNT` | 機器の状態として記録する |
| `TIM` | 現在時刻(`TIME`)を返す |
| ダウンロードの種別(`PTG`・`EDG`・`FBK`・`SBK`・`GEN`・`AGN`・`COA`・`FSG`・`LMD`・`DNL`。7.4.3)・要求 ID | ジョブ番号を、送信待ちのデータに付けた名前(6 章)と照らして探し、見つかればそのデータで応答する(6 章の送信データ作成に従う)。初期化しない機器には、要求の種別のプリセットの項目一式を返す |
| 上記以外で規格(表 A.3)にある種別(`CMD`、`LNF` など) | `STATUS=16` を返す |
| 規格にない種別 | `STATUS=16`(要求種別が不明)を返す |
| `REQ` レコードがないパケット | `ANS=ERR` と `STATUS=18` を返す |

- ジョブが見つからないときは `STATUS=1` を返し、記録に確かめること(名前が違う・送信待ちにしていない・送信済み)を書く
- 加工機に渡せないとき(STATUS=4)は、記録に値を含まない日本語の理由を書く。値を含む詳しい理由は、管理画面の一覧と詳細に出す(索引と記録のファイルには残さない)
- アップロードのデータのパケットにも `JOB` が要る(7.1.6)。無ければ `STATUS=7`、要求の `JOB` と違えば `STATUS=6` で断り、保存しない
- シェルフ・切り抜き・厚みのデータセット(`SHLFFMT`・`CRIBFMT`・`STHKFMT`)は、TRCFMT と同じに取り決める(5.8.1・5.10.5・5.11.3)。機器が申し出た形式から 1 つ選んで返す。作り直さないので、保存した形(形式・点数・角度のモード)が取り決めと違えば、その加工機には渡さない(STATUS=4)。求められたのにジョブに無ければ、見出しを 0 にして示す(`SHLFFMT=0` など)
- 要求 ID の記録が無いとき(初めて・入れ直し・`dataDir` を変えた)は、時刻(秒)から番号を始める(7.2.3.3。前に割り当てた番号と重ならないように)
- `JOB` の無い要求には、`STATUS=7`(足りないレコード)と説明 `JOB` を返す(7.1.6 は初期化の外の全てのパケットに JOB を求める。表 A.24 の 7 は、足りないレコードのラベルを説明に書くとする)
- アップロードの `JOB` が値の長さの上限(255 文字。附属書 D の 3.13 の改訂)を超えれば、`STATUS=6` で断る(索引と受信データの情報に残すため)
- 加工機に向けて作り直せないとき(保存した `DRILLE` の基準が取り決めた基準と違う、機器ごとの値を決められない など)は `STATUS=4` を返し、送信待ちのまま残す。表 A.24 の 4 は「データはあるが、求めた機器には合わない」、8 はホストの内部の誤りを表すため。渡す直前の検査で vca-hub が送信待ちから外したときは、機器に合わないのではなく vca-hub が人に確かめ直してもらうために止めたので、`STATUS=8` に説明 `job held for review` を添える
- 割り当てていない要求 ID で要求してきた機器には `STATUS=5`(初期化が必要)を返す
- 応答では、受け取ったジョブ番号を返す。値の前後の空白は除く(`vca-parser.js` の読み方。5 章の注記は、空白を読みやすさのためのものとしている)
- 初期化しない機器の `EDG` には、プリセットの項目一式を返す(7.2.6.2。項目は `VCA.presetRecords`)。持っていない項目は `?`(左右一対のレコードは `?;?`。5.1.4)
- 初期化しない機器は、玉型・サグ・穴あけの基準の希望を要求に書く(7.2.8・5.4.11.2・5.5.3)。玉型は、機器が書いた順に、扱える形式の最初のもので送る。サグ(ZFMT)を求めたら `ZFMT=0` で答える。穴あけの基準は、機器が書いた候補のうち、ジョブの DRILLE の基準に合うものを使う。玉型の形式を書いたのに扱える形式が 1 つも無ければ `STATUS=17` に、表 A.25 の修飾子(形式 256・点数 512・角度のモード 1024)のうち当てはまるものを足して返す(5.4.17)
- アップロード(受け取ったまま保存し、作り直さない)では、角度のモード C も受け、点数の上限を設けない
- ダウンロードで扱える玉型の形式は、形式 1-4、角度のモード E・U、眼 R・L・B、点数 3-3600(書かなければ受け取ったまま)とする。規格に点数の上限は無いが、作り直す点数に上限が無いと 1 つの応答が際限なく大きくなるため。上限は、360 度を 0.1 度刻みで表せる点数とした(規格の例は 400 点)。初期化でも同じ確かめをする
- 初期化しない機器が `DEV` を書かなければ、要求の種別(`REQ`)を機器の種類とする(7.2.1 は、初期化しない機器は REQ のプリセットの機器の種類を使うとする。7.2.6.2 の例にも DEV は無い)
- 初期化した機器も、要求に `TRCFMT`・`ZFMT`・`DRLFMT` を書けば、そのセッションだけ初期化の取り決めに代わる。次のセッションは初期化の取り決めに戻る(7.2.3.2)
- 玉型の無いジョブでサグを求めた機器には、`TRCFMT=0` に続けて `ZFMT=0` も返す。5.4.1 は TRCFMT=0 が ZFMT=0 を含むので要らないとし、7.2.8 はサグを扱わないホストは ZFMT=0 を返すとする。付けても 5.4.1 に反しないので、7.2.8 に合わせる
- 初期化の名乗り(DEV・VEN・MODEL・SN・MID)の値が 255 文字を超えるか、定義の名前が 12 文字(limited。表 A.2・5.1.8.3)を超えれば、`STATUS=13` で断る(要求 ID の記録に残すので、長い値を繰り返されると記録が膨らみ、書くたびに止まるため)
- 記録に無い要求 ID(数の上限で古いものから消したもの)の要求には、何を送るか分からないので、知らない要求 ID として `STATUS=5` を返す(7.2.1。機器が初期化し直す)
- 送る項目に `BEVP` があれば、BEVP の値によって要る `BEVM`・`BEVC` も送る(7.2.4.3、表 A.7 の注記)。表 A.1 の BEVP の意味から、1・2・5 は `BEVM`、3 は `BEVM` と `BEVC` を要るとし、0・4・7・10 はどちらも足さない。左右で違えば、どちらかで要るものを足す。BEVP が無い・`?`・意味の決まっていない値(6・8・9 など)のときは、要るかどうか決められないので両方足す(ジョブに無ければ `?`)
- 機器ごとのレコード(`PROC`・`PROCBLK`。5.16・5.17)は、加工機が名乗った機器(初期化の DEV・VEN・MODEL・SN、初期化しない機器は要求の DEV・VEN・MODEL)に合うものだけを、機器を示す欄を除いて渡す。`PROC`・`PROCBLK` の行とブロックの中身は、そのままは渡さない(5.16)。決まりは 6 章の「送信データ作成」
- 加工機へのダウンロードは、データのパケットに加工機が ACK を返してから送信済みにする。ACK が来なければ送信待ちのまま残す
- 1 つのデータを 2 台の加工機に渡さない。ジョブを探すときに、そのデータを応答する接続のために押さえ、ACK を受けて送信済みにするまで、ほかの接続には渡さない。その間に同じジョブを求めた機器には `STATUS=11` を返す(表 A.24 の 11 は、受け手が忙しく、いまは要求に応えられないことを表す。送り終えた後に求めれば `STATUS=1`、送り終えられなければ渡せるので、ジョブが無いとは答えない)。押さえていることは索引に残さない(送っている途中で vca-hub が止まったら、起動し直したときは送信待ちに戻る)
- ACK が来ないまま再送の上限を過ぎたとき、または接続が切れたときは、押さえたデータを放して送信待ちに戻し、記録(`download-unconfirmed`)に残す。加工機がデータを受け取って ACK だけが届かなかったのか、受け取っていないのかは、DCS の手順からは見分けられない。もう一度渡す前に、加工機に届いていないかを人が確かめられるようにするため
- 通信方式の拡張(13 章)も、同じ仕組みでデータを押さえる(`io.reserve`)。拡張の機器へ渡している途中のデータを VCA の加工機が求めたときも `STATUS=11` を返す。名前で探すだけのとき(`io.queued`)も、ほかの相手へ渡している途中のデータは返さない
- 要求 ID は再起動をまたいで繰り返さない通し番号にし、`devices.json` に残す(7.2.3.3)。同じ名乗りの機器が初期化し直しても、前の要求 ID は消さない(名乗り(VEN・MODEL・SN)だけでは機器を見分けられず、製造番号を名乗らない同じ機種が何台もあるときや、1 つのアドレスの向こうに何台もあるときに、ほかの機器が使っている要求 ID を消してしまうため。増えすぎは数の上限で抑える)。つないでいるほかの接続にも、割り当てた要求 ID を知らせる(機器がつなぎ直しても `STATUS=5` にしないため)
- 要求 ID の記録は 500 件までとし、超えたら古いもの(先に割り当てたもの。作った時刻ではなく番号で決める。時計が戻ったときに、割り当てたばかりの要求 ID を消さないため)から消す(名乗りを変えて初期化を繰り返されても、記録と 1 回ごとの処理が増え続けないように)。消した要求 ID は、つないでいる接続からも外す
- 自動フォーマット初期化のラベル一覧は、英字か `_` で始まり、英数字・`_`・`.`・`-` が続く 16 文字までのラベル(5.1.6)を 1000 個までとし、重なりは 1 つにする。正しくないラベルがあるか多すぎれば、初期化を断る(`STATUS=13`。大きな一覧を繰り返されると、要求 ID の記録が膨らみ、書くたびに止まるため)
- 初期化の応答の `TRCFMT` は 5 つの欄をすべて書く(表 A.2)
- 対応しない要求種別に返す番号は、表 A.24 の定義(16: ホストが要求の種類を特定できない)に合わせる。本文の 7.6.2・7.7.2 は 8 と書くが、表 A.24 の 8 はホストの内部エラーであり、vca-guide と同じく本文の誤記とみる(詳しくは vca-guide の `docs/conformance.md` の「規格書の中の食い違い」)

### 機器役(別の PC やソフトへの送信)

- 相手のホストへ接続し、`REQ=UPL` でアップロードする。名乗りは `DEV=UPL`(汎用アップロード機器)、`VEN`・`MODEL` は vca-hub 自身。受け取った元の機器の `DEV`・`VEN`・`MODEL` は通信用のレコードなので、付け直す(6 章)
- 送り先ごとの設定で、`REQ=TRC`(`DEV=TRC`)に変えられる(トレーサーからのデータだけを受け付けるホストのため)
- 送るデータは、機器用のレコードすべてと玉型。玉型を送る機器は、初期化か要求のパケットで TRCFMT を申し出る(5.4.1・7.2.8)。全てのホストが対応する形式 1 だけを申し出て、玉型も形式 1 にして送る(申し出は 1 つなので、点数と角度のモードは 1 つ目の玉型にそろえ、左右は受け取ったまま。相手の返事を待ってから玉型を作り直せないため)。玉型が無ければ申し出ない
- 別の PC への送信や共有フォルダへの書き出しをしても、加工機向けの送信待ちは外さない(送った記録だけを足す)
- ジョブ番号は、vca-hub で付けた名前(6 章)
- 相手が初期化を求めてきた場合(`STATUS=5`)は初期化してからやり直す
- 相手が `STATUS=0` 以外を返したら失敗として記録し、画面に表示する。ホストの説明文はそのまま出す(A.4)
- 初期化のデータの応答が `STATUS=0` 以外なら、要求 ID(DEF)があっても続けない(A.4: 0 以外はセッションを中止させる)。要求 ID が無い・整数でないときは、データを送らずに失敗にする(7.2.4.4・7.2.5.4・表 A.2)。応答の STATUS が 0 でも、送信済みにしない
- 送り先に届いたか分からないときは、送れなかったときと分けて知らせ(`upload-unconfirmed`)、送信済みにしない。データのパケットに ACK を受けた後で切れた・最後の応答が来ない・最後の応答に STATUS が無い(A.4 は応答に必ず入るとする)ときである。送り直すと送り先に同じジョブが 2 度届くことがあるので、送り先で受け取ったかを確かめてもらう
- アップロードのセッション全体に期限(120 秒)を設ける。応答を少しずつ送ってくる相手は、文字の間の時間切れにかからず、いつまでも終わらないため
- シェルフ・切り抜き・厚みのデータセットは、保存した形式のまま申し出る。DRILLE があれば、その基準(2 つ目の欄の 1 文字目)を DRLFMT で申し出る(5.5.3)
- ホストが応答(または初期化)で申し出と違う玉型の形式を返したら、記録に残す(7.2.8 はホストが申し出の 1 つを返すとする。データは申し出の形式で送る。返事を待ってから作り直せないため)

### 共通

- 確認応答(ACK/NAK)、再送 3 回、タイムアウト(確認応答 6 秒、パケット 12 秒、文字間 5 秒)は規格どおり。初期化で `TIMEOUT` を指定された場合はそれに従う
- CRC は相手が付けてきたら検証し、こちらも付けて返す
- バイナリ形式の玉型データでは、予約制御文字のエスケープを規格どおりに処理する
- 順序が崩れた(同期ずれ)ときは `STATUS=12` を送ってセッションを中止する(表 A.24)
- 同時に複数の機器と通信できるが、1 台の機器とのセッションは 1 つずつ処理する

## 6. 保存と送信データ作成

### 保存

```
data/
  inbox/2026-10-18/
    A0001_143005_tracer1.vca     受信した原文(バイト列のまま。手を加えない)
    A0001_143005_tracer1.json    受信情報(受信元、日時、要求種別、玉型の寸法など)
  index.json                     一覧用の索引
  index.json.bak                 1 つ前の索引(索引が読めないときに読む)
  devices.json                   初期化で割り当てた要求 ID と機器の希望(devices.json.bak は 1 つ前のもの)
  import-pending.json            「取り込み済み」へ移したが、まだ保存を終えていないファイルの印(6 章)
  pending-delete.json            索引から外したのに、ほかのソフトが開いていて消せなかったファイル(消し直す)
  log/2026-10-18.log             送受信の記録(レコードの中身は書かない。ファイルの日付と記録の時刻は UTC)
```

- 索引と要求 ID の記録は、一時ファイルに書いてディスクへ書き切って(fsync)から名前を変える。置き換える前のものは `.bak` に残す(読めるものだけ)。電源断などで読めなくなったときは、`.bak` から読み、記録に残す。`.bak` からは、最後の 1 つの変更が抜けることがある。要求 ID は、同じ番号を 2 度割り当てないよう通し番号を進める(7.2.3.3)。どちらも読めなければ起動しない(消えたデータを黙って空として扱わないため)
- 受け取った本文と情報のファイルも、ディスクへ書き切ってから(fsync)索引に載せる(機器には保存できてから STATUS=0 を返すので、電源断で中身だけが失われないように)
- 違うラベルが 2000 種類を超える本文は、読まずに断る(TCP の機器には STATUS=8、取り込みでは「取り込めなかった」へ移す)。加工のデータとしてありえない本文で、読み取りと保存・検査の手間やメモリを使わないため
- ログには、値の長さを切って書く(1 つの値は 300 文字、detail は 2000 文字まで)。ジョブ番号や機器の名乗りは相手から届いたままなので、長い値を繰り返されると、ログのファイルと画面に返す一覧が際限なく大きくなるため。索引のジョブ番号は 255 文字までにし、送り出せない理由と知らせは 20 件まで、1 つ 300 文字までにする(値は 40 文字まで)
- 索引を 1 つ前のものから戻したとき、消し直しを待っているファイルの記録は登録し直さない(人の削除や保存期間で消したものを生き返らせないため)。形の違う索引を 1 つ前の索引(.bak)に写さない
- 索引は、要素ごとに形(id と本文のファイルの場所があること)も確かめ、違えば 1 つ前の索引から読む。古い版の記録で欠けている欄(送った記録の一覧)は補う
- 索引の変更は、途中で例外になったときも、書けなかったときも、メモリの索引を元に戻す(画面の状態とファイルが食い違わないように)
- 加工機から ACK を受けたのに送信済みを書けなかったもの(ディスク不足など)は、送信済みとして押さえたままにし、保存期間の処理(1 時間ごと)で書き直す。接続が切れても放さない(放すと、同じジョブをほかの機器にもう一度渡すため)。止まった後は送信待ちに戻る(11 章)
- 1 つ前の索引から読んだときは、最後の変更が抜けているので、受信データのファイルと突き合わせる。本文のファイルが無い記録は外す(抜けたのが削除だった)。索引に無い受信データは、受け取ったときに一緒に書いた情報のファイル(`.json`)から登録し直し、「戻したもの」の印を付ける(抜けたのが受信で、機器にはもう STATUS=0 を返したかもしれないので、黙って消さない)。送信待ちのものは、送信待ちから外す(抜けたのが送信済みだったかもしれず、2 度渡さないため。人が確かめ直して戻す)。突き合わせた結果は記録に残す
- 索引を書く途中で止まったときの一時ファイル(`index.json.tmp`・`devices.json.tmp`)は、起動するときに消す。書き出しの途中で止まったときの、書き出し先の一時ファイル(`.<名前>.<プロセスの番号>.tmp`。個人情報を含む)は、起動するときと 1 時間ごとに消す。消すのは、動いていないプロセスの、10 分より前に書かれたものだけ(ほかの vca-hub が書いている途中のものを消さない)
- 消すときは、先に索引から外してからファイルを消す。ほかのソフトが開いていて消せないファイルは覚えておき、1 時間ごとに消し直す(例外にせず、記録に残す)。索引に無いまま残ったファイル(異常終了・`.bak` から読んだときなど)は、保存期間を過ぎたら消す。期間の中のものは、索引から外れた理由が分からないので残す。消し直す一覧はデータのフォルダ(`pending-delete.json`)に残し、起動し直しても消し直す。消し直すのはデータのフォルダの中のファイルだけとする(一覧は絶対のパスなので、フォルダを写して移した後に、元の場所を消さないように)。索引を 1 つ前のものから戻したときは、一覧のうち索引にある本文・情報のファイルを外す(戻した記録の本文を消さないため)
- 保存期間の処理は、消す記録をまとめて索引から外し、索引を書くのは 1 回とする(件数ごとに書き直すと、その間 vca-hub が止まる)。索引の .bak は、このプロセスが書いたか読めた索引(大きさと時刻が変わっていないもの)なら写し、そうでなければ読んで確かめてから残す
- 記録を消して索引を書いたあとは、1 つ前の索引(.bak)も今の索引と同じにする(消した記録のジョブ番号・名前を .bak に残さないため)
- 送受信の記録(ログ)のファイルの日付と記録の時刻は UTC とする(受信データのフォルダの日付は、その PC の日付)。管理画面の「記録」には、起動してからの直近 500 件のうち 200 件を出す(起動し直す前の記録は、ログのファイルで見る)
- 送受信の記録(ログ)を保存期間で消すときは、画面に出す直近の記録(メモリ)からも消す。拡張が受信データごとに残した情報(`data/ext/<名前>/<id>.json`)のうち、索引に無く保存期間を過ぎたものも消す(拡張そのもののファイルは消さない)。書く途中で止まった一時ファイル(`<id>.json.tmp`)も同じに消す

- 受信した原文は加工せずに保存する(何を受け取ったかを後から確認できるようにするため)。例外は次の項目の場合だけ
- 個人情報項目の除去を有効にしている場合は、7 章の項目を除いたものを保存し、除く前の原文は保存しない
- 同じジョブ番号を再度受信した場合は上書きせず、別のファイルとして残す
- ファイル名に使えない文字や、フォルダをさかのぼる指定(`..` など)はジョブ番号から取り除く

### 名前

受け取ったデータは、人が名前を付けるまで、どこへも渡さない(加工機への送信待ち、別の PC への送信、共有フォルダへの書き出しのどれにも使えない)。vca-hub は中継と保管の場所であり、名前の付いていないものは出荷しない。

- 名前は、送信先へのジョブ番号(`JOB`)として使う。`JOB` は通信用のレコードなので、付け替えても 1 章の中継の方針に反しない
- 送信待ちのデータの名前は変えない。書き出し・送り先への送信の確認で違う名前を入れたら断る(名前を変えると、同じ名前が 2 つ送信待ちになったり、加工機が求めた名前で見つからなくなるため)。名前を変えるときは、先に送信待ちから外す
- 加工機へ渡している途中(ACK を待っている)のものは、送信待ちから外すことも、名前を変えることも、ほかのデータで置き換えることもしない(同じ名前で中身の違うものが 2 台に渡ったり、取り消したのに渡したものが送信済みになるため)。画面では、渡し終えてから操作するよう知らせる。削除も断る(渡したのに、索引にもファイルにも残らなくなるため)。一覧と詳細には、渡している途中であることと、索引を戻したときの印を状態に添えて出す
- 書き出し・送り先への送信の名前は、成功してから付ける(失敗したのに名前だけ変わらないように)。送り先へ送っている間に別の名前で送信待ちにされて名前を付けられなくても、届いたことは送った記録に残す(どの名前で送ったかも書く)
- 名前を付けるのは、送信前の確認(下記)と同じとき。受け取ったデータに `JOB` があれば、入力欄に候補として出すが、人が確かめて決めるまでは名前が付いたことにしない
- 保存した原文の `JOB` は、受け取ったまま残す。名前は索引(`index.json`)に残す
- 送信待ちの別のデータと同じ名前は付けられない(加工機は名前で求めるので、同じ名前が 2 つあると、どちらを渡すか決められない)。前のものを送信待ちから外してから付けるかを、画面で選ぶ
- 名前は、ファイル名に使えない文字とフォルダをさかのぼる指定を含められない(書き出しのファイル名にもなるため)
- 名前は JOB の型(limited)に合わせ、12 文字まで、文字の範囲 32-127 とする(5.1.8。vca-guide の `docs/conformance.md`。127 は、vca-lens-simulator・vca-ptn-converter と同じく使えるとする)。vca-hub は文字コードを ASCII で取り決めるので、日本語などは加工機へ正しく届かない
- 値の区切りの `;` は使えない(JOB の値が `;` の前で切れ、加工機が求めたジョブ番号と合わなくなる)
- Windows の装置の名前(`CON`・`NUL`・`COM1` など。拡張子を付けたものも)は使えない。書き出した `CON.vca` を、ほかのソフトがファイルとして開けないため

- Windows が装置として扱う名前(`CON`・`NUL`・`COM1` など。Windows 10 は最初の `.` より前を、末尾の空白を除いて比べるので `CON .A` も含む)は、名前にできない。受け取った JOB がそうした名前のときは、受信データのファイル名の前に `_` を付ける(ほかのソフトで開けず、手で消しにくいファイルを作らないため)

### 共有フォルダ

- 書き出し: ファイル名は `名前.vca`。同じ名前のファイルがあれば上書きできる(受け取る側のソフトがファイル名を決め打ちしていることがあるため)。上書きになるときは、送信前の確認の画面で知らせ、上書きしたことをログに残す。上書きするのは、確認の画面で上書きを知らせたときだけとする。確認の後に同じ名前のファイルが現れたときは上書きせずに断り、画面で知らせ直す(同じ名前があれば失敗するハードリンクで置く。ハードリンクを作れないフォルダでは、確かめてから置く)。書き出し先のフォルダを作れない・書けないときは、理由(`export-failed`)を画面に出す。確認の画面では、書き出したファイルに個人情報が含まれることがあり、書き出し先を誰が読めるかは利用者が管理することを知らせる
- 送り先への送信: 送っている途中のデータは、消すことも断る(届いたのに送った記録が残らなくなるため。保存期間の処理でも消さない)。送り終えるまでもう一度は送らない(画面のボタンを 2 度押しても、同じジョブが 2 度届かないように。`uploading` で断る)
- 取り込み(フォルダ監視): 取り込んだファイルは、監視するフォルダの中の「取り込み済み」のフォルダへ移す(すぐには消さず、保存期間を過ぎたら消す。7 章)。VCA ファイルとして読めなかったものは「取り込めなかった」のフォルダへ移し、ログに理由を残す。取り込んだデータも、受け取ったデータと同じく、名前を付けるまで渡さない
- 取り込みで「取り込めなかった」へ移すのは、VCA ファイルとして読めないもの(VCA のレコードが無い)と、大きすぎるもの(1 MiB を超える。VCA の口のパケットの上限と同じ。読むと vca-hub が長く止まるため)だけとする。ほかのソフトが開いていて読めない・移せないときと、vca-hub の側で保存できないときは、ファイルの誤りではないので、移さずに次の回にやり直す(記録は同じファイル・同じ理由なら 10 分に 1 度)
- 取り込むフォルダの中のリンクは辿らない(外のファイルを読み込まない)。「取り込み済み」「取り込めなかった」がリンク・ジャンクションで取り込むフォルダの外を指していれば、そこへ移すことも、そこのファイルを保存期間で消すこともせず、記録に残す
- 取り込むフォルダが読めない・作れない(共有フォルダの PC が止まっているなど)ときも、vca-hub は止めない。加工機の中継は続け、取り込みは読めるようになるまで回ごとにやり直す(記録は 10 分に 1 度)
- ネットワークの共有フォルダ(`\\server\share` の形)は、読み書きの前に、vca-hub を止めない形で届くかを確かめる(2 秒)。届かなければ、取り込みはその回を飛ばして記録に残し、書き出しと書き出し先の確認は断る。届かない共有フォルダへの読み書きは、Windows の接続待ちの間(実測で約 27 秒)vca-hub 全体を止め、加工機とのセッションが時間切れになるため
- 取り込むフォルダと書き出し先には、ドライブの直下(`Z:\`)も使える
- 1 回の走査で取り込むのは 20 件までとし、残りは 0.2 秒あけて続ける(数千のファイルを置かれても、1 度に長く止まらないように)
- 取り込むファイルは、先に「取り込み済み」へ移してから読む。書く側が開いたままのファイルは移せないので、書きかけのものを読まない(最後の書き込みから 2 秒たったかだけでは、書く側が途中で止まっているときに見分けられないため)。移した後は元のフォルダに残らないので、2 度取り込まない。更新時刻が未来のファイル(書いた PC の時計が進んでいるなど)は、時刻では書き終えたかを見られないので、前の回から大きさと時刻が変わっていなければ書き終えたとみなす(初めて見たときは記録に残す)
- 移す前に、移す先の名前と使い捨ての番号をデータのフォルダ(`import-pending.json`)に残し、保存を終えたら消す。番号は、受信データに残す取り込み元(`source`)を一意にするため(同じ名前のファイルを後でまた取り込んだとき、前の取り込みと取り違えて取り込まないことがないように)。移した後・保存の前に止まったら、起動し直したときに取り込み直す。保存の後・印を消す前に止まったときは、受信データに残した取り込み元(`source`)と照らして、2 度は取り込まない。保存できない(vca-hub の側の失敗)ときと、移した後に読めないときも、印を残して次の回に取り込む。印が空になったら、1 つ前の印(.bak)も空にそろえる(取り込んだファイルの名前を残し続けないため)
- 印を 1 つ前のものから読んだ・読めなかったときは、移した後・保存の前に止まったファイルが抜けているかもしれない。記録(error)に残し、取り込み済みのうち、1 つ前の印を書いた時より後に移したもの(1 つ前の印が無ければ 1 日以内)で、取り込み元の記録の無いものを取り込み直す(それより前に移したものは取り込み終えている。人が消した取り込みを生き返らせないため)
- 書き出し先と取り込むフォルダが同じか、片方がもう片方の中にあれば、起動しない(書き出したものを取り込み直し、同じデータが重なって登録されるため)。大文字・小文字の違いは、Windows では同じとみなす

### 送信データ作成

保存した原文から、送信先に合わせたパケットを組み立てる。1 章の中継の方針に従い、レコードの値は変えない。

1. 通信用レコード(`REQ`、`ANS`、`JOB`、`STATUS`、`CRC`、`DEV`、`VEN`、`MODEL`、`SN`、`DEF`、`D`、`ENDDEF` など)を取り除き、機器用のレコードだけを残す。玉型データ(`TRCFMT`、`R`、`A`、`ZFMT`、`Z`、`ZA`)は手順 4 で作り直す
2. 送信先に合わせて通信用レコードを付け直す(`ANS`、`JOB`(付けた名前)、`STATUS=0`、`DO` など)。送り手の名乗り・つなぎ方(`HID`・`MVER`・`IP`・`PORT`)と、データのパケットに現れない `DRLFMT`(5.5.3)も取り除く
   - `DO` は、玉型などの左右のデータがあるかどうかにかかわらず、どちらのレンズを加工するかを表す(表 A.2)。受け取ったジョブの `DO` をそのまま送る。玉型の有無や、機器が求めた玉型の向き(TRCFMT の眼)からは決めない。ジョブに `DO` が無いときだけ、玉型のある眼から決める(玉型も無ければ B)
3. 送信先が初期化で受け取りたいレコードを指定している場合、またはプリセットの項目一式を期待する場合は、その項目だけを返す。持っていない項目は `?` で返す(左右一対のレコードは、派生レコード(LD・INS・CK・TOL など)も含めて `?;?`。5.1.4・A.1.1.7)。穴あけの基準(DRLFMT)を取り決めた機器には、ラベル一覧に無くても `DRILLE` を送り、廃止された `DRILL` は送らない(5.5.1.5)。保存した `DRILLE` の基準が取り決めた基準と違えば、作り直せないので、その加工機には渡さない(STATUS=4)。`DRILL` だけのジョブも、基準が分からず `DRILLE` に作り直せないので渡さない(STATUS=4。黙って穴の無いデータにしない)。DRILLE の基準は、2 つ目の欄の 1 文字目(C・E・B)で比べる(2 文字目以降は穴の側と取り付ける面。5.5.2.2)。欄が空なら中心基準とし、R(相対基準)は制御する穴に従うので比べない。穴の無いこと(`DRILLE=0`、2 つ目の欄の 0)と分からないこと(`DRILLE=?`)は、基準によらず渡す。基準を取り決めた機器で、ジョブに穴あけの情報が無ければ `DRILLE=?` を送る(5.5.2.10.9)。基準を取り決めていない加工機には DRILLE を使えない(5.5.1.5)ので、穴のある DRILLE を持つジョブは渡さず(STATUS=4)、一覧で求められたら `DRILLE=?` を送る。初期化で選ぶ基準は、機器が申し出た順に vca-hub が扱える最初のものになる。初期化の時点ではジョブが分からないので、後で求められたジョブの基準と合わないことがある(そのジョブは STATUS=4)。5.5.1.5 は初期化しない機器は DRILLE を使えないとし、5.5.3 は要求に DRLFMT を書けるとする。vca-hub は 5.5.3 に合わせ、要求の DRLFMT も受ける
4. 玉型データは、送信先が求める形式(1-4)、点数、角度のモード(E・U)、左右の向きに合わせて変換する(ホストが返す TRCFMT は実際に使うもの。7.2.8)。機器が 1 組だけを求めた(眼が R か L)ときは、加工する眼(`DO` が R・L ならその眼、B・N なら求めた向きの眼)の玉型を、求めた向きにして送る。その眼の玉型が無ければ、反対眼のものを反転して使う(5.4.13)。ただし、片眼の玉型と左右で違う `CIRC`(または `CIRC3D`)があり、`BSIZ`・`CSIZ` が無いか分からないときは反転しない。このときの左右の周長の差は、送らない眼の形を変える量(暗に示した `CSIZ`)を表す(5.4.9.4)。反転して寸法を元の眼の値にそろえると、この差が消えるので、受け取った向きと寸法のまま送る(加工機はどちらの向きも受けなければならず、ホストが向きを合わせるのは「できるとき」。5.4.13)。形式を取り決めていない(初期化しない機器が要求に TRCFMT を書かないなど)ときは、全ての機器が扱える形式 1 で送る(7.2.8。点数・角度のモード・向きは受け取ったまま)。玉型が無ければ、玉型を求めた機器にだけ `TRCFMT=0` を送る(5.4.1。vca-hub が形式を決めた送り先・書き出しには付けない)
5. 共有フォルダへの書き出しでは、1 行目を `REQ=FIL`、2 行目を `JOB` にし、制御文字・`CRC`・`STATUS` を入れず、玉型データは形式 1 にする
   - 玉型(TRCFMT)とサグ(ZFMT)のデータセットは作り直す。ほかのデータセット(CRIBFMT・STHKFMT など)は、見出しのあとの系列の行(R・A・T など)を見出しと一緒にそのまま送る(5.1.9・5.10.4・5.11.1)。見出しの無い系列の行は送らない
6. 機器ごとのレコード(5.16・5.17): 加工機へは、名乗った機器に合う `PROC` を「ラベル=右;左」として、合う `PROCBLK` のブロックの中身を番号(`1!` など)を除いて渡す。`PROC`・`PROCBLK` の行とブロックの中身は、どの加工機へもそのままは渡さない。別の PC・共有フォルダへは、受け手が機器に合わせるので、そのまま残す(ブロックの中身は宣言に続けたまま)
   - 合うかどうか: DEV は必ず合うこと。VEN・MODEL・SN は空なら絞らない(表 A.1)。合った欄が多いほど、その機器に向けたものとする(5.9.3.2 の LDPATH の、左からできるだけ多くの欄が合うものを選ぶ決まりと同じ考え)
   - 複数置けるレコード(表の P)は、全体のものに足す(5.17.1.1)。1 つしか置けないレコードは、合った欄がいちばん多いもので全体の値を置き換える
   - 同じ合い方で値の違うものがあれば、どれを渡すか決められないので、その加工機には渡さない(STATUS=4 を返し、送信待ちのまま残す。理由は記録に残す)
   - 機器向けの玉型・データセット(ブロックの中の `CRIBFMT`・`R` など)は作り直せないので、そのブロックに合う加工機には渡さない(同じく STATUS=4)。送信前の確認で、機器ごとの値があることと、渡せないブロックを知らせる
   - 形の崩れたもの(PROC の値の欄が無い・ラベルか DEV が空、PROCBLK の番号か DEV が空・同じ番号の宣言、宣言の無い・宣言から離れたブロックの行、PROC やブロックの中の PROC・PROCBLK)は、送り出せない理由にする(表 A.1)
   - PROC の 1 つ目の欄は、機器に渡すときのラベルになるので、ラベルの形(英字か `_` で始まり、英数字と `_` だけ)でなければ送り出さない(`=` や `*` を含むと、2 つ目の `JOB` や別のラベルとして読まれるため)。個人情報の項目の除去では、1 つ目の欄を行の頭と同じ読み方(前後の空白・制御文字・`*` を除き、`=` より前)で読む
   - `LDPATH` の機器ごとの形(`DEV;VEN;MODEL;SN;種類;パス[;左のパス]`。5.9.3.2)は、名乗った機器に合う欄がいちばん多いものを 1 つ選び、パスの欄だけを `LDPATH` に、種類を `LDTYPE` にして渡す(種類が空なら SDF)。機器が受け取る `LDPATH` は 1 つだけ。1 つ目の欄が整数の形は LDS から LMS へ送るもので、機器には渡さない(5.9.3.3)。合うものが無ければ元の 1 欄の形を渡す。決められないときは渡さない(STATUS=4)。受け取りたい一覧に `LDPATH` があれば `LDTYPE` も送る
   - LDS から LMS への形(1 つ目の欄が整数の `LDPATH`、2 欄の `LDCRYPT`。暗号化した面データ。5.9.3.3・5.9.7.4)は、機器へ渡す形に作り直せないので、その加工機には渡さない(STATUS=4)
   - 名乗った機器と大文字・小文字だけが違う `PROC`・`PROCBLK` があれば、書き誤りか名乗りの揺れか分からないので、全体の値を黙って渡さず、その加工機には渡さない(STATUS=4)
   - 機器が DEV を名乗らない(初期化が無く、要求の DEV も種別も機器を表さない、拡張の通信方式が機器を渡さない)ときは、合うかどうか決められないので、全体の値を黙って渡さず、その加工機には渡さない(STATUS=4)。名乗っていない欄(VEN・MODEL・SN)で絞った値は、その機器には合わないとし、表 A.1 の優先順位どおり下の段を使う(初期化しない機器は SN を名乗らないので、SN で絞ったブロックは当てはまらない)

- 1 つしか置けないレコード(5.1.10)が同じ値で 2 つあれば、1 つだけ送る。左右一対のレコードの値が 1 つの形(両眼に当てはめる)や、片眼だけの注文で片方を空にした形(`SPH=;2.75`)は、5.1 が認める形なので変えない
- 反対眼の玉型を反転して送るときは、寸法(`CIRC`・`HBOX`・`VBOX`・`CIRC3D`)の送る眼の値を、反転した形の寸法(元の眼の値)にする(5.4.9.3)。左右の周長が違い、寸法の変更(`BSIZ`・`CSIZ`)が無いか分からない片眼の玉型は、反転しない(5.4.9.4。上の 4)。送る前の確認には、反転するかどうかを出す
- `LDTYPE` が無ければ `SDF` として送る(5.9.3.2: 無ければ SDF とみなす。種類は ? にできない)。PROC に入った `LDPATH`・`LDTYPE` は、全体の値に足さずに置き換える(機器が受け取る LDPATH は 1 つ)。`LDCRYPT` を送るなら、`EDATA` をその後に続ける(5.9.7.4)。`ENGMARK` の種類が DCS なら、指すレコードもデータに入れる(5.15.1.3)
- 機器ごとの値の優先順位は、表 A.1 のとおり、合う欄の多いもの(DEV+VEN+MODEL+SN、DEV+VEN+MODEL、DEV+VEN、DEV)から使う。機器が名乗っていない欄(初期化しない機器の SN など)で絞った値は、その機器には合わないとし、下の段へ進む(表 A.1 が段の順を一意に決めているため)。機器が DEV を名乗らなければ、決められないので断る
- データセットの途中の `REM` は、データセットを閉じない(REM はどのパケットにも置ける。系列の続きを落とさないため)。系列の行は、その見出しの系列のもの(CRIBFMT なら R・A、STHKFMT なら R・A・T など。5.8-5.14)だけを付け、ほかの見出しの系列の行は見出しの無い行として送らない(vca-parser と同じ読み方)
- ラベルは、英字か _ で始まり、空白と予約文字(表 1: 制御文字と `; = , * ? |`)を含まないものとして読む(5.1.6)。`.`・`-`・`:` は予約文字ではないので、`ACME.X`・`ACME:MODE` のような行も落とさずに送る。拡張の出力の確かめも、同じ読み方をする(拡張を入れたかどうかで、送れるデータが変わらないように)
- 角度のモード C の玉型(角度が増えも減りもする。鍵穴のような形)は、角度を並べ替えずに受け取った順のまま送る。等角度にも増えていく角度(U)にも作り直せないので(5.4.3.1)、E・U を取り決めた加工機には渡さない(STATUS=4)

### 送信前の確認

加工の取り違えを防ぐため、別の PC やソフトへの送信と、共有フォルダへの書き出しの前に、画面で次を確認してから実行する。

- 名前(ジョブ番号)、左右、玉型の形(拡大図)、送信先
- 共有フォルダへの書き出しでは、同じ名前のファイルがあって上書きになること
- `DO` が値違いで 2 回ある、R・L・B・N 以外の値(`?` を含む)のときは、加工するレンズが決まらないので送り出さない。`DO` が無ければ、玉型のある眼から決めることを知らせる
- 1 つしか置けないレコード(5.1.10)が 2 回以上あれば、値が違うときは送り出さない(加工機がどちらを使うか決まらないため)。同じ値なら知らせる
- 玉型の眼が R・L でない(B など)とき、同じ眼の玉型が 2 つ以上あるときは送り出さない(データの玉型は眼ごとに 1 つ。5.4.12)。確認の画面に描く形と、渡す玉型が食い違うため
- 送り出せない理由にするもの: ASCII 以外の文字(5.1.8。vca-hub は ASCII だけを取り決める)、1 つのジョブの DRILLE の基準の混ざり(5.5.1.5)、`LDTYPE=?`(5.9.3.2)、種類が SDF なのにパスが 2 つの LDPATH(5.9.3.2)、ENGMARK が指すレコードが無いこと(5.15.1.3)、CIRC3D があるのに FCRV が無いこと(サグは中継しないので。5.4.9.5)、BSIZ と CSIZ の両方に 0 でない値(5.4.9.2)
- データセットの決まりに合わない値(角度・重みの範囲、数の食い違いなど)は、読み取りの警告から知らせる。後ろの余分な区切り(`DO=L;`)は無いものとして読む(5.1)
- バイナリの形式のデータセットの系列に、逃がしていない予約文字(FS・GS・RS など。5.1.7.3)があれば、送り出せない理由にする(加工機の側でパケットが切れるため)
- 穴あけが DRILL だけのジョブ、注記(REM)のあるジョブは、そのことを知らせる(DRILL だけでは穴あけの基準を取り決めた加工機に渡せない。注記は送らない)
- サグ(ZFMT)のデータがあれば、中継しないので、どの送り先にも送らないことを知らせる
- 点数が 3 未満の玉型は、形にならないので送り出せない理由にする(送ると、加工機には玉型が無いと答えることになるため)
- データセットの系列の行(T・S・ZZ・PP など)は、系列を複数のレコードに分けて書くので、1 つしか置けないレコードの重なりとして数えない(5.1.9)
- `DO` は literal なので、大文字・小文字を区別する(5.1.8.4)。`DO=b` は R・L・B・N のどれでもないとして止める
- 規格外の行(長い行・ASCII 以外の文字)の知らせは、ラベルごとにまとめ、名前を出すのは 10 種類までとする(行の多いデータで、知らせと索引が膨らまないように)

加工機への送信は加工機からの要求に応答する形のため、送信待ちにする時点で同じ確認を行い、名前を付ける。加工機に渡す直前(加工機の要求に応えるとき、通信方式の拡張が `io.records` で作るとき)にも、送り出せない理由ができていないかをもう一度確かめる(拡張の加工条件を外した・変えたなど)。理由があれば渡さず(STATUS=8)、送信待ちから外して記録に残し、人に確かめ直してもらう。拡張の例「加工条件」は、送信待ちのものの条件を変えることも外すことも断る(人が確かめたのと違う条件を渡さないため。変えるときは、先に送信待ちから外す)。拡張に渡す `store.get`・`store.list` も、索引の記録の写しとする。例「加工条件」は、受け取りたい一覧に BEVP があれば、条件の BEVM・BEVC も送る(7.2.4.3)。別の PC・共有フォルダへは、条件と同じラベルの PROC とブロックの行を外す(受け手がそちらを優先して、人が確かめたのと違う条件が届かないように)

## 7. 個人情報の扱い

VCA の注文データには、装用者の氏名(`CLIENT`、`CLIENTF`、`CLINIT`)、年齢(`CLAGE`)、処方度数などが含まれることがある。これらは個人情報保護法上の個人データにあたる場合があるため、次の措置をとる。

- 個人情報項目の除去: 有効にすると、受信時に氏名・年齢などの項目を除いてから保存する。既定は有効。行の頭やラベルの後ろに空白・制御文字・8 ビットの文字があっても、ラベルの大文字・小文字が違っても除く。読み取りがその項目として読む行は、全て除く。PROCBLK のブロックの中の行(`1!CLIENT=` など)と、1 つ目の欄が個人情報の項目の PROC(`PROC=CLIENT;EDG;;;氏名`。機器にはその項目として渡るため。1 つ目の欄を引用符で囲んだ `PROC="CLIENT";…` も、読み取りと同じく引用符を外して読む)も除く。拡張の通信方式から受けた本文は、ファイルに書くのと同じ 1 文字 1 バイトの形にそろえてから除く(1 バイトで表せない文字が下位の 1 バイトになって、除いた後に改行や別のラベルができないように)
- 除く項目は、表 A.1 で装用者(Wearer)の項目とされるもの(`CLAGE`・`CLDEYE`・`CLFRNT`・`CLHLAT`・`CLHT`・`CLIENT`・`CLIENTF`・`CLINIT`・`CLLIFE`・`CLLNAM`・`CLNVB`)と口座番号(`ACCN`)である。処方度数、レンズに刻む文字(`ENGMARK`)、注記(`REM`)、`_` で始まる独自の項目、ファイルのパスなどは、加工に要るか中身を決められないので除かない。取り込むファイルの名前も、装用者の名前のことがある(受信データの記録に、取り込み元として残る)
- 保存期間: 既定は 90 日とし、過ぎたデータを自動で削除する(設定で日数を変えられ、`null` で無期限)。送信待ちのものは、加工機がまだ取りに来ていないので消さない。送信待ちから外したもの(人が外した、渡す直前の検査や索引を戻したときに vca-hub が外した)は、外した時から数える(外した直後に消すと、人が確かめ直して送信待ちに戻す前に無くなるため)。保存期間の「今」は、起動したときの時計に、動いている間の経過時間を足したものとし、動いている間に時計を変えられても、その分を経過したとして一度に消さない(ずれが 1 時間を超えたら記録に残す)。受け取った順に並んだ索引で、前に受け取ったものより古い時刻のもの(時計が遅れていた間に受け取ったもの)は、前のものの時刻から数える。1 つ前の索引から読み直したときも、索引の並びは変えない(登録し直したものは後ろに足す。時刻で並べ替えると、遅れた時刻のものが先頭に来て、この守りが外れるため)。保存期間を 30 日より多く過ぎたものは、自動では消さずに残し、件数を記録に出す(`purge-held`)。1 時間ごとに消しに行くので、ふつうは期間を過ぎた直後に消える。大きく過ぎたものは、前に受け取ったものが無いまま時計が遅れていた(新しく入れた PC で時計が古い年に戻っていた、など)か、長く止めていたかで、vca-hub には見分けられないので、人が受け取った時刻と中身を確かめて消す。「今」より先の時刻のもの(時計が進んでいた間に受け取ったもの)は、その前に受け取ったものの時刻から数え、後のものの基準にもしない。動いている間に時計を戻したときはすぐに従い、進めたときは起動し直すまで経過した時間だけを数える。起動する前から時計が誤っていたときは見分けられないので、時計は正しく合わせておく(11 章)。送受信の記録(日ごとのファイル)と、共有フォルダから取り込んだ元のファイル(個人情報の項目を除く前のもの。移した時から数える)も、同じ期間で消す。記録にはジョブ番号と名前が残るため。消したことはログに残す
- 記録: 送受信の記録(ログ)には、ジョブ番号、相手、結果だけを書き、レコードの中身は書かない。加工機へ渡せない理由は、値を含まない日本語の説明と id だけを書く(理由の文には PROC や LDPATH の値が入るため。値を含む理由は管理画面に出す)。保存期間で消したことの記録には、id と件数だけを書き、名前や取り込んだファイルの名前は書かない(新しい日の記録に写して、保存期間より長く残さないため)
- アクセス: データの保存先フォルダは、利用する Windows アカウントだけが読み書きできるようにすることを推奨する(README に記載する)
- 共有フォルダへの書き出し: 書き出し先を誰が読めるかは利用者の管理とし、画面で注意を表示する
- 外部への送信: 別の会社(外部のラボなど)へ送る場合は、個人データの第三者提供または委託にあたる。同意の取得や委託契約などは運用側で整える

## 8. 管理画面

見た目と並びは、vca-lens-simulator・vca-ptn-converter にそろえる(上の帯、左のタブ、右の図の面、下の帯にボタン。角を立て、影を使わず、区切りは罫線、色はアクセント 1 色。明るい配色と暗い配色)。

- 上の帯: 待ち受けているポート、送り先、名前なし・送信待ちの件数
- 左の「受信」タブ: 一覧。玉型の縮小図、名前(付けていなければ「名前なし」)、受け取った JOB、左右、日時、受信元、状態(名前なし、未送信、送信待ち、送信済み。加工機・送り先へ送っている途中、送信済みを書けていない、渡す直前の検査や索引を戻したときに送信待ちから外した、の印を添える)、送れない理由・注意の印。すべて・名前なし・送信待ち・送信済みで絞り込める
- 送る前の確認の画面は、開くときに詳細を読み直す。確かめた中身(本文・送り出せない理由と知らせ・拡張の説明)から作った値を添えて送り、vca-hub は送る直前に作り直して比べ、違えば送らない(`changed`)。送っている間は、閉じることも、もう一度押すこともできない
- 一覧は、変わっていなければ中身を送らない(管理画面は 3 秒ごとに読み直す。索引の変更・押さえ・送り先へ送っている途中・拡張の情報の変更の通し番号で見分ける)。拡張の検査の結果は覚えておき、状態・名前・拡張の情報(`hub.data`)が変わったものだけ検査し直す。送信済みのものには検査しない
- 送信待ちのものを消すときは、加工機が求めても渡せなくなることを確認の文に出す。vca-hub が止まった後に画面が戻ったら、設定(書き出し先・送り先・拡張)を読み直す
- 左の「記録」タブ: 送受信のログとエラー(新しいものが上)
- 左の「設定」タブ: 待ち受けているポート、送り先、書き出し先、取り込むフォルダ、個人情報項目の除去、保存期間、データの保存先、初期化した機器(変更は `config.json` で行う)
- 右の面: 「玉型」は正面から見た向きで、右眼を左、左眼を右に、DBL の間をあけて並べ、箱と中心の線、寸法を添える。「内容」は受け取ったときの情報と全レコード、「原文」は受信した原文
- 拡張: 拡張がページを持てば、右の面のタブに出す。拡張からの説明(足す加工条件など)は、詳細と送る前の確認に出す(13 章)
- 下の帯: 名前・左右・玉型の寸法・DBL・状態と、送信待ち・取り消し・書き出し・送り先へ送る・削除のボタン。送る操作は、どれも送信前の確認(6 章)の画面を経る。同じ名前が送信待ちのときと、送れなかったときは、確認の画面の中で知らせる
- 書体: PC に入っている BIZ UDPゴシック(本文)と BIZ UDゴシック(名前・数値・レコード)を使い、外へ読みに行かない。Web フォント版の BIZ UDゴシックは、小さい字でハイフンと下線が消えることがあり、名前を見誤るため

管理画面はこの PC からのみ開ける。ほかのサイトの枠(iframe)には入れさせない(`X-Frame-Options: SAMEORIGIN`・`frame-ancestors 'self'`。押し間違いを誘う画面を作らせないため。拡張のページは同じオリジンの枠なので通す)。管理画面には認証が無いので、待ち受けるアドレス(`web.host`)は、この PC のもの(`127.0.0.1`・`::1`)のほかは起動しない。要求ごとに、相手のアドレスがこの PC のものかも確かめる(Host ヘッダーは相手が自由に書けるため)。この PC のほかの利用者・ほかのプロセスからは開けるので、vca-hub を動かす PC は、共用しないものを使う

- 形の崩れた PROC・PROCBLK(値の欄が無い・同じ番号の宣言・宣言から離れた行など)は送り出さず、名乗った機器と大文字・小文字だけが違うものがあれば加工機に渡さなかった(`tests/device-specific.test.js`)

- プリセット初期化をした加工機へのプリセット一式、別のホストへ送るときの TRCFMT の申し出と形式 1、渡す直前の検査、1 つしか置けないレコードの重なり、索引を戻して記録を外したときの起動、.bak に消した記録を残さないこと、取り込むフォルダが読めないときに止まらないこと、同じ名乗りの機器が何台もあるときの要求 ID(`tests/consistency.test.js`)

## 11. 既知の制約

- 実機での動作は保証できない。機種ごとに規格と食い違うところや、規格が機器に任せているところ(独自レコード、初期化の有無、形式の選び方)は、実機でしか分からない
- RS-232C だけを持つ機器とはつなげない
- ホストによっては、大きいデータのパケットを受けられない。DCS v3.14 にパケットの大きさの上限は無いが、DCS Host Simulator(The Vision Council)は、約 12 KB を超えるデータのパケット(例: 両眼 1440 点の形式 1 の玉型)を受け取らず(ACK を返さない)、その後は起動し直すまで次の接続も受けなかった。1 回で書き込む量が約 10 KB を超えたときも、同じように受け取らなかった。vca-hub は玉型を受け取った点数のまま送るので(送り先が形式を決めないとき。6 章)、点数の多い玉型をこのようなホストへ送るときは、送り先で受け取れたかを確かめる
- 何も送らない接続を、時間で閉じない(4 章)。許可範囲の中の相手が接続を開いたままにできるのは、接続の数の上限(`connections`)までとする。上限に達すると、ほかの機器の新しい接続も断る。許可範囲を狭く書いて使う
- 管理画面には認証が無い。この PC のほかの利用者・ほかのプロセスからは操作できる(8 章)
- 通信方式の拡張の待ち受けは、接続の数を vca-hub では限らない(拡張が限る。vca-hub-extension の OLDP はハンドシェイクの前の接続を限る)
- アップロードの途中で強制終了すると、本文のファイルだけが索引に載らずに残ることがある(機器には STATUS=0 を返していないので、機器が送り直す)。残ったファイルは、保存期間を過ぎたら消す
- 加工機の ACK を受けてから送信済みを索引に書くまでの間に止まると、送信待ちのまま残り、もう一度渡すことがある(受け取った知らせと書き込みを 1 つにできないため)
- 電源断で索引が読めなくなったときは、1 つ前の索引から読むので、最後の 1 つの変更(受け取った・送ったなど)が抜けることがある
- 書き出しで上書きしないときは、同じ名前があれば失敗するハードリンクで置く。ハードリンクを作れないフォルダ(FAT・exFAT、一部のネットワークのフォルダ)では、確かめてから名前を変えるので、その間に現れたファイルは上書きしてしまう
- 上限に達したときに断る接続には、DCS の応答(STATUS)を返さない(要求を読む前に閉じる)。機器には、つながらなかったことだけが分かる
- keepalive で閉じるまでの時間は OS による。Node.js の文書では、確かめは 1 秒おきに 10 回とされ、何も届かなくなってから 70 秒ほどで閉じる見込みである。Windows で応答しない相手を作って測ってはいない(作るにはファイアウォールの設定を変える必要がある)
- 書き出し先と取り込むフォルダを、同期ソフト(OneDrive など)や共有先どうしの同期でつなぐと、vca-hub からは重なりを見分けられず、書き出したものを取り込み直す。書き出し先を同期から外して使う。書き出したファイルの重なりを見つける仕組み(中身の識別など)は、今後の候補とする
- 拡張は vca-hub と同じプロセスで動く。拡張の同期の処理が終わらない(無限の繰り返しなど)と、vca-hub 全体が止まる。止めることも、時間で打ち切ることもできない
- 拡張のタイマー・イベントなどの中の例外(同期)は捕まえられないので、vca-hub は記録に残して止まる。拡張の Promise の失敗は記録に残して動き続ける(13 章)
- vca-hub が消すのは `data/` と取り込むフォルダの中と、書き出し先に vca-hub が残した書きかけの一時ファイル(`.名前.番号.tmp`)だけである。バックアップ・シャドウコピー・同期・書き出した先の複製は、利用者が管理する
- 通信方式の拡張が `io.reserve` を使わずに渡すデータは、押さえない。その間に VCA の加工機や別の機器が同じジョブを求めれば渡す(例の拡張 text-protocol と、vca-hub-extension の OLDP は `io.reserve` を使う)
- 規格書(DCS v3.14)に従って作るが、規格への準拠は保証しない
- vca-hub は加工用のデータを中継するだけで、診断や処方の決定は行わない。このため薬機法上の医療機器プログラムには当たらないと考えるが、最終的な判断は所管官庁の基準による
- 配布する場合は、無保証であること(データの誤りによる加工の失敗などに責任を負わないこと)を明記する

- 異常終了の後、止まった vca-hub のプロセスの番号を別の node のプロセスが使っていると、ロックを引き継がずに起動しない。そのときは、ほかに vca-hub が動いていないことを確かめてから、`data/vca-hub.lock` を消す

- 起動する前から PC の時計が誤っていると、保存期間を正しく数えられない。時計が進んでいれば早く消し、遅れていれば遅く消す。動いている間の時計の変更は数えない(7 章)

- 割り当てたネットワークドライブ(`Z:` など)は、ローカルのドライブと見分けられないので、届くかを前もって確かめない。共有フォルダは UNC のパス(`\\server\share`)で書く
- 索引は 1 つの JSON のファイルで、変えるたびに全体を書き直す。件数に比例して重くなり、実測では 5 万件(1 日約 550 件を 90 日)で 1 回 0.5 秒ほど止まる。忙しいラボでは、保存期間を短くして件数を抑える

## 13. 拡張

vca-hub は中継に徹し、受け取った中身は変えない(1 章)。加工条件を足す、メーカー独自の項目や、規格から外れたメーカーの通信に合わせる、といったことは、利用者が作って入れる拡張で行う。派生する人が vca-hub 本体を書き換えずに済むようにするため。

### 置き方と読み込み

- 拡張は 1 つのフォルダ(`extensions/<名前>/index.js`)。`config.json` の `extensions` に名前を書いたものだけを読む(`{ "<名前>": 設定 | true }`)。拡張のコードは vca-hub と同じ権限で動くので、フォルダに置いただけでは読まない
- 書いた拡張が読めない・`setup` で失敗したときは、vca-hub を起動しない。加工条件の拡張が欠けたまま、条件なしで加工機へ渡さないため
- フックは同期で答える。フックが Promise を返したら、失敗を捕まえて記録に残す。結果を使うフックでは、Promise を失敗として扱う(`check` は送り出せない理由に、`send` は送らない、`describe` は説明を作れなかったことを確認の画面に出す。`send` が送るデータを変えることがあるので、人が確かめないまま送らないように)。拡張の通信方式などで捕まえていない Promise の失敗は、記録に残して動き続ける。捕まえていない例外(同期)は、状態が分からないので止める
- フックと `io` が拡張に渡す索引の記録は写しとする。拡張が書き換えても、索引(状態・名前・ファイルの場所)は変わらない。状態を変えるのは、`io` の関数(`markSent` など)と、人の操作(送信前の確認)だけにするため。`io.records` は、渡された記録の id で索引の記録を引き直して読む
- `io.records` は、そのデータが今も送信待ちで、名前が変わっていないかを確かめる(`io.queued` で見つけた後に、人が取り消した・置き換えたデータを渡さないため)。送り出せない理由が見つかったら、押さえを放してから送信待ちから外す(加工機への応答と同じ。押さえたままだと、人が消すことも送信待ちに戻すこともできない)
- `io.markSent` で送信済みを書けなかったとき(ディスク不足など)は、送信済みとして押さえたままにし、保存期間の処理で書き直す(VCA の加工機と同じ。ほかの相手に同じジョブを渡さない)
- `io.markSent(id, to, { name })` は、送信待ちであること、ほかの相手(VCA の加工機・ほかの口)が押さえていないことを確かめる。押さえた相手は、同じ口の `io.reserve` で押さえた記録で見分ける。`name` を渡せば、送信待ちのものの名前とも照らす(`io.queued` で探して渡したときに、渡した後で人が名前を変えたものを送信済みにしないため)
- 拡張に渡す設定(`hub.settings`・口の `settings`・送り先の `dest`)と時間切れの設定(`io.timeouts`)は写しとする。拡張が書き換えても、`config.json` から読んだものと DCS のセッションの時間切れは変わらない
- `extensions` で `false` にした拡張は読まない。読む順は `config.json` に書いた順で、`send` もその順に通す(ただし JavaScript の決まりで、数字だけの名前は先になる)
- `hub.data.set` は、受信データが無ければ(消された後など)`not-found` を投げる
- 拡張は `module.exports = { title, version, setup(hub) }` の形。`setup` に渡す `hub` だけを通して vca-hub とやりとりする
- 例を `examples/extensions/` に置く(加工条件、メーカー別の項目、テキストの通信方式)。配る zip にも入れる

### フック

| フック | 呼ぶとき | できること |
|---|---|---|
| `received` | 受信データを保存したあと(どの通信・取り込みでも) | 拡張の情報を付ける。失敗しても受信は取り消さない(記録に残す) |
| `check` | 送り出す前の検査(送信待ち・書き出し・送り先への送信)と、一覧の印 | 送り出せない理由・注意を足す。拡張の検査が失敗したら、送り出せない理由にする(安全な側に倒す) |
| `send` | 送るレコードを作るとき(加工機への応答、共有フォルダ、送り先) | レコードを足す・変える・外す。送り先の種類(`device`・`file`・`destination`)、加工機が名乗った機器(DEV・VEN・MODEL)と求めた項目が分かる。失敗したら送らない(加工機には STATUS=8 を返し、送信待ちのまま残す) |
| `describe` | 詳細と送る前の確認の画面 | 拡張が足す・変えることの説明を出す(人が確かめてから送れるように) |
| `queued` | 送信待ちにしたとき | 通信方式の拡張が、つないでいる機器へ知らせる |

- 受け取った本文(保存したファイル)は、拡張も変えられない。拡張が変えるのは、送るときに作るレコードだけ
- `send` が足した・変えた・外したラベルは、拡張の名前と一緒に記録に残す
- `send` が返したレコードは形を確かめ、正しくなければ送らない。ラベルは英字か _ で始まり、英数字・_・.(メーカーの名前空間)が続く(前にブロックの番号 `n!` と `*` を付けてよい)。値に制御文字(CR・LF・FS・GS・RS など)があってはならない(書き出しのファイルや送り先へ、別のレコードが紛れ込むため)。セッションの見出しのレコード(`REQ`・`ANS`・`STATUS`・`JOB`)は vca-hub が付けるので、足すことも変えることもできない
- 管理画面の拡張の API が返すものは JSON にできる値とする。できなければ、誤りの応答を返す
- 拡張は受信データごとの情報を `data/ext/<名前>/<id>.json` に残せる。受信データを消すと一緒に消える。拡張そのものの情報(通信方式の鍵、組み合わせた相手など)は、同じフォルダ(`hub.dataDir`)に置ける
- 管理画面: 拡張は API(`/api/ext/<名前>/<path>`)と、右の面のタブに出すページ(拡張のフォルダの中の HTML。選んだ受信データの id を渡す)を持てる。変更を伴う API は、ほかの API と同じく独自ヘッダーを確かめる。ページが中身を変えたら、親の画面に知らせて一覧と詳細を読み直させる

### 通信方式

規格から外れたメーカーの通信に合わせるため、拡張は通信方式を足せる(`hub.protocol(id, { listen, connect, upload })`)。

- 口ごとに通信方式を選ぶ。待ち受け(`remote` と、追加の `listeners`)、ローカル接続(`local`)、送り先(`destinations`)のそれぞれに `protocol` を書く。書かなければ、または `vca` なら DCS。VCA の口とメーカーの口を並べられる(トレーサーは VCA、加工機はメーカーの通信、など)
- 保存の形は、どの通信方式でも VCA のテキストにそろえる。通信方式の拡張は、相手の形と VCA のレコードとの間を変換するだけで、保存・人が付けた名前で探す・渡している途中のデータを押さえる・送信済みにする、は vca-hub が行う(拡張に渡す `io`)。名前を付けるまで渡さない決まり(6 章)と、送る前の検査は、通信方式によらず同じ
- 書いた通信方式がどの拡張にも無い、または口に要る働き(待ち受けなら `listen`)が無ければ、起動しない
- 拡張の `upload` は、データを送った後で応答が無いなど、届いたか分からないときは code `unconfirmed` の例外にする(vca-hub が送れなかったときと分けて知らせ、送り直しを誘わないため)。送る前の失敗は、そのほかの例外にする
- 管理画面の一覧の拡張の検査の結果は、受信データの状態・名前・その受信データの拡張の情報(`hub.data`)が変わるまで使い回す。拡張の検査は、これらだけに依るようにする(ほかのファイルや時刻に依ると、一覧の印が古いまま残る。送る直前には毎回検査し直す)
- 送る前の確認では、取り違えにつながりやすいことを知らせる: 付けた名前が受け取った JOB と違う(大文字・小文字だけの違いも。加工機は区別して求める)、前に送ったことがある、同じ JOB の後に受け取ったデータがある(測り直したもの)。止めはしない(ジョブ番号を付け直す運用があるため)
- 拡張の `listen` が 30 秒で終わらなければ、起動を止める(後の待ち受け・ローカル接続・管理画面が起動しないまま残らないように)。`upload` が 120 秒で終わらなければ、届いたか分からないとして知らせ、送っている途中の印を外す(後で届いたと分かったら、送った記録を残す)。`connect` は止める関数を返す。Promise を返したら、解決した止める関数を使い、失敗したら記録に残す
- 管理画面の「設定」に、口ごとの通信方式と、読んだ拡張を出す。選ぶのは `config.json` で行う(管理画面からの設定の変更は範囲外。1 章)

### できないこと

- DCS のセッションの中で、規格に無い要求の種類(メーカー独自の `REQ`)を受けること。vca-guide の `createHost` が、表 A.3 に無い種類を vca-hub に渡す前に断るため。そうした機器は、DCS ではない通信方式として拡張で扱う
- PROC・PROCBLK のブロックの中の玉型・データセットを、その機器に合わせて渡すこと(6 章。合う加工機には渡さない)

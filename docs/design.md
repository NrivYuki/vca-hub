# vca-hub 設計書

眼鏡店・ラボの機器と PC の間で VCA 通信(DCS v3.14)のデータを受け取り、ローカルフォルダに保持し、任意の送信先へ中継する常駐プログラム。

この文書は vca-hub の設計をまとめたものである。主な決まりは 12 章、拡張は 13 章にまとめる。

## 1. 目的と範囲

- 必須条件: 送られてきたデータをローカルフォルダに保持し、任意の送信先にそのまま送信(中継)できること
- 受信元: トレーサー、別の PC(機器としてアップロードしてくる場合、または共有フォルダにファイルを置く場合)
- 送信先: 加工機、別の PC やソフト、共有フォルダ
- 接続: LAN(TCP/IP)。リモート接続、ローカル接続、オートコネクトの 3 方式
- 機器の機種は限定しない(規格どおりに動く機器を対象とする)
- 実行環境: Node.js(Windows を主対象とする)
- 配る形: インストールなしで動かす。node.exe を同梱したフォルダを zip にし、展開して起動用のファイル(`start.bat`)を開くだけで動くようにする(管理者の権限を要らなくするため)。データは同じフォルダの `data/` に置く。`start.bat` は同じフォルダの `node\node.exe` を先に使い、無ければ PC に入っている Node.js を使う(zip にする前の元のフォルダでも、同じ `start.bat` で起動できる)

### 中継の方針

- 受け取ったデータの中身(レコードの値)は変えない。足りない項目を補ったり、推測で埋めたりしない(例外は 7 章の個人情報項目の除去を有効にした場合だけ)
- 素材、ヤゲン位置、加工の種類などは加工機側で決める前提とし、vca-hub は扱わない。扱いたい利用者は拡張で足す(13 章)
- メーカー独自の項目や、規格から外れたメーカーの通信も、vca-hub 本体では扱わず、拡張で足す(13 章)
- 変えてよいのは、規格上必要な「入れ物」の部分だけとする
  - パケットの組み立て直し(通信用レコードの付け替え)
  - 玉型データの形式・点数・左右の向きを、送信先の機器が求める形に合わせること
  - 送信先が求めたレコードを持っていない場合に、値の代わりに `?`(不明)を入れること

### 範囲外

- レンズ設計、度数計算、厚み計算
- 処方を決めたり変えたりする機能(入れない)
- 足りない加工項目の入力・補完
- RS-232C(シリアル)接続。12 章の主な決まりを参照
- 管理画面の検索・設定画面、Windows のサービス化などの常駐化(設定は `config.json` で行う)

## 2. 前提となる規格上の制約

- 通信は必ず機器(デバイス)から始まる。ホストから機器へ一方的に送り付ける手順はない。vca-hub から接続しにいく場合(ローカル接続、オートコネクト)でも、接続後にセッションを始めるのは機器側である
- そのため「送信」は送信先ごとに次の形になる
  - 加工機: 保持したデータを送信待ちにしておき、加工機からの要求(`REQ=EDG` とジョブ番号)に応答する
  - 別の PC やソフト(相手がホスト): vca-hub が機器として相手へアップロードする(`REQ=UPL` または `REQ=TRC`)
  - 共有フォルダ: VCA ファイル(`REQ=FIL` 形式)として書き出す
- 受信も同様で、別の PC から受け取れるのは、相手が機器としてアップロードしてくる場合か、ファイルを置く場合に限られる
- 加工機はジョブ番号でデータを要求する。トレーサーには入力の手段が無く、意味のあるジョブ番号を送れないことがあるので、受け取ったデータには vca-hub で人が名前を付け、その名前を加工機・別の PC・共有フォルダへのジョブ番号にする(6 章の「名前」)

## 3. 全体構成

```
                         +--------------------- vca-hub(Node.js) ---------------------+
[トレーサー]    --LAN--> 接続部 --> セッション処理(ホスト役) --> 保存部 --> data/
[別の PC]       --LAN-->          |                                ^
[共有フォルダ]  ------> フォルダ監視 -------------------------------+
                         |                                                  |
[加工機]        <--LAN-- 接続部 <-- セッション処理(ホスト役) <-- 送信待ち一覧
[別の PC/ソフト] <-LAN-- 接続部 <-- セッション処理(機器役)   <-- 送信指示
[共有フォルダ]  <------ ファイル書き出し <------------------------- 送信指示
                         |
                         +- 管理画面(http://localhost:8765、この PC からのみ)
```

| 要素 | 役割 | 実装 |
|---|---|---|
| 接続部 | TCP の待ち受け・接続、オートコネクト(UDP)、許可する IP アドレスの確認 | vca-guide の `vca-tcp.js`。許可範囲の確認は vca-hub 側で行う |
| パケットの送受信 | FS から GS までの切り出し、ACK/NAK、再送、タイムアウト、CRC、同期ずれの検出 | vca-guide の `vca-session.js`(`createLink`) |
| セッション処理(ホスト役) | 初期化と形式の取り決め、アップロード受信、ダウンロード応答、時刻合わせ | `vca-session.js` の `createHost`。応答の中身は vca-hub が `onInit`・`onRequest`・`onData`・`onNotify` で返す |
| セッション処理(機器役) | 別の PC やソフトへのアップロード | `vca-session.js` の `createDevice` |
| 要求 ID の保存 | 初期化で割り当てた要求 ID と、機器が求めたレコード・玉型形式を再起動をまたいで保持する | vca-hub(`createHost` の `nextRequestId` と `onInit` につなぐ) |
| 保存部 | 受信データの保存、索引の更新、個人情報項目の除去(設定時) | vca-hub |
| 送信データ作成 | 保存データから送信用のレコードを組み立てる(1 章の中継の方針に従う) | vca-hub |
| フォルダ監視 | 指定フォルダに置かれた VCA ファイルの取り込み | vca-hub |
| 管理画面 | 一覧、玉型表示、送信前の確認、送信先の指定、送受信記録 | vca-hub |
| 読み書き | レコードの読み取り、玉型形式 1-4 の読み書き、点数の変換、ラベル定義表 | vca-guide の `vca-parser.js`・`vca-records.js` |

### vca-guide のライブラリの扱い

- `vca-parser.js`・`vca-records.js`・`vca-session.js`・`vca-tcp.js` の 4 つを vca-guide の `src` から `src/lib/` に写し、vca-guide と同じものに保つ(vca-lens-simulator・vca-ptn-converter も、このうち `vca-parser.js`・`vca-records.js` を写している)。同じであることはテスト(`tests/e2e.test.js`)で確かめる
- vca-hub で直したいところが見つかったら、vca-guide で直してから写し直す。vca-hub の中では書き換えない
- 理由: パケットの送受信とセッションの手順は vca-guide 側で規格書から決めたテストと DCS Host Simulator との照合を経ており、同じものを vca-hub で別に持つと、直すたびに 2 か所の食い違いが生じるため
- 規格の読み方で vca-guide と同じ判断になるところ(STATUS の番号など)は、vca-guide の `docs/conformance.md` に従う
- vca-hub が使う、vca-guide のライブラリの働き
  - `vca-session.js` の `createHost` の `onComplete`: 要求のセッションの最後のパケットにデバイスが ACK を返したあとに呼ぶ。加工機が受け取ったことを確かめてから送信済みにするため
  - `vca-tcp.js` の `listenHost` の `opts` に渡す関数: 接続ごとに設定を作り、`null` なら接続を切る。相手のアドレスを記録に書くためと、許可範囲の外の相手を断るため
  - `vca-tcp.js` の `listenAutoconnect` の `opts.connectOpts`: オートコネクトでつなぐたびに設定を作る(同じ理由)

## 4. 接続(LAN)

規格の 3 つの接続方式すべてに対応する。

| 方式 | 動き | ポート |
|---|---|---|
| リモート接続 | vca-hub が待ち受け、機器から接続してくる | 33512(変更可) |
| ローカル接続 | 機器が待ち受け、vca-hub から接続しにいく(機器の IP を設定) | 機器側 50000(変更可) |
| オートコネクト | 機器が UDP で自分の IP とポートを知らせ、vca-hub がそこへ接続する | 33511 で受信 |

- 接続後、機器は 3 秒待ってからセッションを始める(規格の決まり)
- 別の PC やソフトへ送るときは、vca-hub が相手のホストへ接続する(相手の IP とポートを設定)
- 接続を受け付ける IP アドレス、およびオートコネクトで接続しにいく IP アドレスは、設定した許可範囲に限る(VCA 通信自体には認証の仕組みがなく、不正な通知で意図しない相手に接続することを防ぐため)
- リモート接続は、すべての通信口で待ち受け、相手は許可範囲で限る(`vca-tcp.js` の `listenHost` は待ち受けるアドレスを選べないため)
- ローカル接続は、切れたら 10 秒後につなぎ直す

## 5. セッション処理

### ホスト役(受信と加工機への送信)

| 要求 | 対応 |
|---|---|
| `INI` | 自動フォーマット初期化に対応する。機器が示したレコード一覧に要求 ID を割り当てて返す。玉型形式(`TRCFMT`)・サグ(`ZFMT`)・文字コード(`TXTENC`)は `VCA.negotiate` で取り決める(玉型は形式 1-4、角度のモードは E・U。サグは中継しないので `ZFMT=0`。文字コードは ASCII)。アップロード専用の機器が行うプリセット初期化も受け付ける |
| `TRC`・`UPL`・`INS` | アップロードを受け取り、保存部へ渡す |
| `INF` | 作業完了の通知として記録する |
| `MNT` | 機器の状態として記録する |
| `TIM` | 現在時刻(`TIME`)を返す |
| `EDG`・`DNL`・要求 ID | ジョブ番号を、送信待ちのデータに付けた名前(6 章)と照らして探し、見つかればそのデータで応答する(6 章の送信データ作成に従う) |
| 上記以外で規格(表 A.3)にある種別(`GEN`、`SBK` など) | `STATUS=16` を返す |
| 規格にない種別 | `STATUS=16`(要求種別が不明)を返す |
| `REQ` レコードがないパケット | `ANS=ERR` と `STATUS=18` を返す |

- ジョブが見つからないときは `STATUS=1` を返す
- 割り当てていない要求 ID で要求してきた機器には `STATUS=5`(初期化が必要)を返す
- 応答では、受け取ったジョブ番号を返す。値の前後の空白は除く(`vca-parser.js` の読み方。5 章の注記は、空白を読みやすさのためのものとしている)
- 初期化しない機器の `EDG` には、プリセットの項目一式を返す(7.2.6.2。項目は `VCA.presetRecords`)。持っていない項目は `?`
- 送る項目に `BEVP` があれば、`BEVM`・`BEVC` も送る(7.2.4.3、表 A.7 の注記は、BEVP の値によって必要なら BEVM・BEVC も入れるとする)。どの値のときに必要かは見分けず、いつも足す(ジョブに無ければ `?`)
- 加工機へのダウンロードは、データのパケットに加工機が ACK を返してから送信済みにする。ACK が来なければ送信待ちのまま残す
- 要求 ID は再起動をまたいで繰り返さない通し番号にし、`devices.json` に残す(7.2.3.3)。同じ機器・同じタグで初期化し直したら、前の要求 ID は消す。つないでいるほかの接続にも、割り当てた要求 ID を知らせる(機器がつなぎ直しても `STATUS=5` にしないため)
- 初期化の応答の `TRCFMT` は 5 つの欄をすべて書く(表 A.2)
- 対応しない要求種別に返す番号は、表 A.24 の定義(16: ホストが要求の種類を特定できない)に合わせる。本文の 7.6.2・7.7.2 は 8 と書くが、表 A.24 の 8 はホストの内部エラーであり、vca-guide と同じく本文の誤記とみる(詳しくは vca-guide の `docs/conformance.md` の「規格書の中の食い違い」)

### 機器役(別の PC やソフトへの送信)

- 相手のホストへ接続し、`REQ=UPL` でアップロードする。名乗りは `DEV=UPL`(汎用アップロード機器)、`VEN`・`MODEL` は vca-hub 自身。受け取った元の機器の `DEV`・`VEN`・`MODEL` は通信用のレコードなので、付け直す(6 章)
- 送り先ごとの設定で、`REQ=TRC`(`DEV=TRC`)に変えられる(トレーサーからのデータだけを受け付けるホストのため)
- 送るデータは、機器用のレコードすべてと、受け取った形式のままの玉型(相手の求めが分からないため)
- 別の PC への送信や共有フォルダへの書き出しをしても、加工機向けの送信待ちは外さない(送った記録だけを足す)
- ジョブ番号は、vca-hub で付けた名前(6 章)
- 相手が初期化を求めてきた場合(`STATUS=5`)は初期化してからやり直す
- 相手が `STATUS=0` 以外を返したら失敗として記録し、画面に表示する

### 共通

- 確認応答(ACK/NAK)、再送 3 回、タイムアウト(確認応答 6 秒、パケット 12 秒、文字間 5 秒)は規格どおり。初期化で `TIMEOUT` を指定された場合はそれに従う
- CRC は相手が付けてきたら検証し、こちらも付けて返す
- バイナリ形式の玉型データでは、予約制御文字のエスケープを規格どおりに処理する
- 順序が崩れた(同期ずれ)ときは `STATUS=12` を送ってセッションを中止する(表 A.24)
- 同時に複数の機器と通信できるが、1 台の機器とのセッションは 1 つずつ処理する

## 6. 保存と送信データ作成

### 保存

```
data/
  inbox/2026-10-18/
    A0001_143005_tracer1.vca     受信した原文(バイト列のまま。手を加えない)
    A0001_143005_tracer1.json    受信情報(受信元、日時、要求種別、玉型の寸法など)
  outbox/                        共有フォルダへ書き出す前の一時置き場
  index.json                     一覧用の索引
  devices.json                   初期化で割り当てた要求 ID と機器の希望
  log/2026-10-18.log             送受信の記録(レコードの中身は書かない)
```

- 受信した原文は加工せずに保存する(何を受け取ったかを後から確認できるようにするため)。例外は次の項目の場合だけ
- 個人情報項目の除去を有効にしている場合は、7 章の項目を除いたものを保存し、除く前の原文は保存しない
- 同じジョブ番号を再度受信した場合は上書きせず、別のファイルとして残す
- ファイル名に使えない文字や、フォルダをさかのぼる指定(`..` など)はジョブ番号から取り除く

### 名前

受け取ったデータは、人が名前を付けるまで、どこへも渡さない(加工機への送信待ち、別の PC への送信、共有フォルダへの書き出しのどれにも使えない)。vca-hub は中継と保管の場所であり、名前の付いていないものは出荷しない。

- 名前は、送信先へのジョブ番号(`JOB`)として使う。`JOB` は通信用のレコードなので、付け替えても 1 章の中継の方針に反しない
- 名前を付けるのは、送信前の確認(下記)と同じとき。受け取ったデータに `JOB` があれば、入力欄に候補として出すが、人が確かめて決めるまでは名前が付いたことにしない
- 保存した原文の `JOB` は、受け取ったまま残す。名前は索引(`index.json`)に残す
- 送信待ちの別のデータと同じ名前は付けられない(加工機は名前で求めるので、同じ名前が 2 つあると、どちらを渡すか決められない)。前のものを送信待ちから外してから付けるかを、画面で選ぶ
- 名前は、ファイル名に使えない文字とフォルダをさかのぼる指定を含められない(書き出しのファイル名にもなるため)

### 共有フォルダ

- 書き出し: ファイル名は `名前.vca`。同じ名前のファイルがあれば上書きする(受け取る側のソフトがファイル名を決め打ちしていることがあるため)。上書きになるときは、送信前の確認の画面で知らせ、上書きしたことをログに残す
- 取り込み(フォルダ監視): 取り込んだファイルは、監視するフォルダの中の「取り込み済み」のフォルダへ移す(消さない)。VCA ファイルとして読めなかったものは「取り込めなかった」のフォルダへ移し、ログに理由を残す。取り込んだデータも、受け取ったデータと同じく、名前を付けるまで渡さない

### 送信データ作成

保存した原文から、送信先に合わせたパケットを組み立てる。1 章の中継の方針に従い、レコードの値は変えない。

1. 通信用レコード(`REQ`、`ANS`、`JOB`、`STATUS`、`CRC`、`DEV`、`VEN`、`MODEL`、`SN`、`DEF`、`D`、`ENDDEF` など)を取り除き、機器用のレコードだけを残す。玉型データ(`TRCFMT`、`R`、`A`、`ZFMT`、`Z`、`ZA`)は手順 4 で作り直す
2. 送信先に合わせて通信用レコードを付け直す(`ANS`、`JOB`(付けた名前)、`STATUS=0`、どちらの眼のデータかを示す `DO=R/L/B` など)
3. 送信先が初期化で受け取りたいレコードを指定している場合、またはプリセットの項目一式を期待する場合は、その項目だけを返す。持っていない項目は `?` で返す
4. 玉型データは、送信先が求める形式(1-4)、点数、左右の向きに合わせて変換する。求めがなければ受信したまま送る
5. 共有フォルダへの書き出しでは、1 行目を `REQ=FIL`、2 行目を `JOB` にし、制御文字・`CRC`・`STATUS` を入れず、玉型データは形式 1 にする

### 送信前の確認

加工の取り違えを防ぐため、別の PC やソフトへの送信と、共有フォルダへの書き出しの前に、画面で次を確認してから実行する。

- 名前(ジョブ番号)、左右、玉型の形(拡大図)、送信先
- 共有フォルダへの書き出しでは、同じ名前のファイルがあって上書きになること

加工機への送信は加工機からの要求に応答する形のため、送信待ちにする時点で同じ確認を行い、名前を付ける。

## 7. 個人情報の扱い

VCA の注文データには、装用者の氏名(`CLIENT`、`CLIENTF`、`CLINIT`)、年齢(`CLAGE`)、処方度数などが含まれることがある。これらは個人情報保護法上の個人データにあたる場合があるため、次の措置をとる。

- 個人情報項目の除去: 有効にすると、受信時に氏名・年齢などの項目を除いてから保存する。既定は有効
- 保存期間: 既定は無期限とし、画面から手動で削除する。設定で日数を指定すると、それを過ぎたデータを自動で削除する。送信待ちのものは、加工機がまだ取りに来ていないので消さない。消したことはログに残す
- 記録: 送受信の記録(ログ)には、ジョブ番号、相手、結果だけを書き、レコードの中身は書かない
- アクセス: データの保存先フォルダは、利用する Windows アカウントだけが読み書きできるようにすることを推奨する(README に記載する)
- 共有フォルダへの書き出し: 書き出し先を誰が読めるかは利用者の管理とし、画面で注意を表示する
- 外部への送信: 別の会社(外部のラボなど)へ送る場合は、個人データの第三者提供または委託にあたる。同意の取得や委託契約などは運用側で整える

## 8. 管理画面

見た目と並びは、vca-lens-simulator・vca-ptn-converter にそろえる(上の帯、左のタブ、右の図の面、下の帯にボタン。角を立て、影を使わず、区切りは罫線、色はアクセント 1 色。明るい配色と暗い配色)。

- 上の帯: 待ち受けているポート、送り先、名前なし・送信待ちの件数
- 左の「受信」タブ: 一覧。玉型の縮小図、名前(付けていなければ「名前なし」)、受け取った JOB、左右、日時、受信元、状態(名前なし、未送信、送信待ち、送信済み)、送れない理由・注意の印。状態で絞り込める
- 左の「記録」タブ: 送受信のログとエラー(新しいものが上)
- 左の「設定」タブ: 待ち受けているポート、送り先、書き出し先、取り込むフォルダ、個人情報項目の除去、保存期間、データの保存先、初期化した機器(変更は `config.json` で行う)
- 右の面: 「玉型」は正面から見た向きで、右眼を左、左眼を右に、DBL の間をあけて並べ、箱と中心の線、寸法を添える。「内容」は受け取ったときの情報と全レコード、「原文」は受信した原文
- 拡張: 拡張がページを持てば、右の面のタブに出す。拡張からの説明(足す加工条件など)は、詳細と送る前の確認に出す(13 章)
- 下の帯: 名前・左右・玉型の寸法・DBL・状態と、送信待ち・取り消し・書き出し・送り先へ送る・削除のボタン。送る操作は、どれも送信前の確認(6 章)の画面を経る。同じ名前が送信待ちのときと、送れなかったときは、確認の画面の中で知らせる
- 書体: PC に入っている BIZ UDPゴシック(本文)と BIZ UDゴシック(名前・数値・レコード)を使い、外へ読みに行かない。Web フォント版の BIZ UDゴシックは、小さい字でハイフンと下線が消えることがあり、名前を見誤るため

管理画面はこの PC からのみ開ける(localhost にだけ公開する)。

## 11. 既知の制約

- 実機での動作は保証できない。機種ごとに規格と食い違うところや、規格が機器に任せているところ(独自レコード、初期化の有無、形式の選び方)は、実機でしか分からない
- RS-232C だけを持つ機器とはつなげない
- 規格書(DCS v3.14)に従って作るが、規格への準拠は保証しない
- vca-hub は加工用のデータを中継するだけで、診断や処方の決定は行わない。このため薬機法上の医療機器プログラムには当たらないと考えるが、最終的な判断は所管官庁の基準による
- 配布する場合は、無保証であること(データの誤りによる加工の失敗などに責任を負わないこと)を明記する

## 13. 拡張

vca-hub は中継に徹し、受け取った中身は変えない(1 章)。加工条件を足す、メーカー独自の項目や、規格から外れたメーカーの通信に合わせる、といったことは、利用者が作って入れる拡張で行う。派生する人が vca-hub 本体を書き換えずに済むようにするため。

### 置き方と読み込み

- 拡張は 1 つのフォルダ(`extensions/<名前>/index.js`)。`config.json` の `extensions` に名前を書いたものだけを読む(`{ "<名前>": 設定 | true }`)。拡張のコードは vca-hub と同じ権限で動くので、フォルダに置いただけでは読まない
- 書いた拡張が読めない・`setup` で失敗したときは、vca-hub を起動しない。加工条件の拡張が欠けたまま、条件なしで加工機へ渡さないため
- 拡張は `module.exports = { title, version, setup(hub) }` の形。`setup` に渡す `hub` だけを通して vca-hub とやりとりする
- 例を `examples/extensions/` に置く(加工条件、メーカー別の項目、テキストの通信方式)。配る zip にも入れる

### フック

| フック | 呼ぶとき | できること |
|---|---|---|
| `received` | 受信データを保存したあと(どの通信・取り込みでも) | 拡張の情報を付ける。失敗しても受信は取り消さない(記録に残す) |
| `check` | 送り出す前の検査(送信待ち・書き出し・送り先への送信)と、一覧の印 | 送り出せない理由・注意を足す。拡張の検査が失敗したら、送り出せない理由にする(安全な側に倒す) |
| `send` | 送るレコードを作るとき(加工機への応答、共有フォルダ、送り先) | レコードを足す・変える・外す。送り先の種類(`device`・`file`・`destination`)、加工機が名乗った機器(DEV・VEN・MODEL)と求めた項目が分かる。失敗したら送らない(加工機には STATUS=8 を返し、送信待ちのまま残す) |
| `describe` | 詳細と送る前の確認の画面 | 拡張が足す・変えることの説明を出す(人が確かめてから送れるように) |
| `queued` | 送信待ちにしたとき | 通信方式の拡張が、つないでいる機器へ知らせる |

- 受け取った本文(保存したファイル)は、拡張も変えられない。拡張が変えるのは、送るときに作るレコードだけ
- `send` が足した・変えた・外したラベルは、拡張の名前と一緒に記録に残す
- 拡張は受信データごとの情報を `data/ext/<名前>/<id>.json` に残せる。受信データを消すと一緒に消える。拡張そのものの情報(通信方式の鍵、組み合わせた相手など)は、同じフォルダ(`hub.dataDir`)に置ける
- 管理画面: 拡張は API(`/api/ext/<名前>/<path>`)と、右の面のタブに出すページ(拡張のフォルダの中の HTML。選んだ受信データの id を渡す)を持てる。変更を伴う API は、ほかの API と同じく独自ヘッダーを確かめる。ページが中身を変えたら、親の画面に知らせて一覧と詳細を読み直させる

### 通信方式

規格から外れたメーカーの通信に合わせるため、拡張は通信方式を足せる(`hub.protocol(id, { listen, connect, upload })`)。

- 口ごとに通信方式を選ぶ。待ち受け(`remote` と、追加の `listeners`)、ローカル接続(`local`)、送り先(`destinations`)のそれぞれに `protocol` を書く。書かなければ、または `vca` なら DCS。VCA の口とメーカーの口を並べられる(トレーサーは VCA、加工機はメーカーの通信、など)
- 保存の形は、どの通信方式でも VCA のテキストにそろえる。通信方式の拡張は、相手の形と VCA のレコードとの間を変換するだけで、保存・人が付けた名前で探す・送信済みにする、は vca-hub が行う(拡張に渡す `io`)。名前を付けるまで渡さない決まり(6 章)と、送る前の検査は、通信方式によらず同じ
- 書いた通信方式がどの拡張にも無い、または口に要る働き(待ち受けなら `listen`)が無ければ、起動しない
- 管理画面の「設定」に、口ごとの通信方式と、読んだ拡張を出す。選ぶのは `config.json` で行う(管理画面からの設定の変更は範囲外。1 章)

### できないこと

- DCS のセッションの中で、規格に無い要求の種類(メーカー独自の `REQ`)を受けること。vca-guide の `createHost` が、表 A.3 に無い種類を vca-hub に渡す前に断るため。そうした機器は、DCS ではない通信方式として拡張で扱う
- PROC・PROCBLK(DCS 5.17。機器ごとの項目を、ひとつのデータの中で機器を指定して渡す規格の仕組み)は、まだ中継していない。規格の仕組みなので、拡張ではなく vca-hub 本体で扱う
